Issue #2147 - The Gateway adopts the pro_selfhost scope table

Branch: feat/gateway-pro-selfhost-scopes   Base: origin/main at 0100a2b5 (rebased onto the merged fourteen-day Pro trial, pull request 2132)   Schema change: none (the entitlements table already admits the tier)

The outcome in one paragraph

The website sells a Pro self-host plan that pays for the artificial-intelligence features only - dictation, text to speech, and the wingman - and explicitly not for hosted capacity. Until this change the Gateway had never heard of that plan: its entitlement read is deliberately tier-agnostic, so any live paid row provisioned a hosted tenant and a device key. The day the paid till opens, a self-host subscriber would therefore have obtained hosted gateway service they never bought, silently - a successful provisioning looks exactly like a correct one. This change gives the Gateway one place that says what a plan grants, and enforces it at the two points where hosted capacity is actually handed out.

What was implemented

  1. One table that owns what a plan grants - new src/CcDirector.Gateway/Tenancy/EntitlementScopes.cs. It maps a tier string to its scope set (dictation, tts, wingman, hosted_gateway) and is the only place in the Gateway allowed to decide what a plan includes. pro_selfhost gets exactly the three artificial-intelligence scopes and no hosted gateway. The table is an allowlist with a deny default: a tier string this code has never been taught grants nothing at all.
  2. The provisioning door refuses - src/CcDirector.Gateway/Api/HostedEnrollmentEndpoint.cs. After the existing money question ("is there a live paid row?") it now asks the plan question ("does that plan include hosted capacity?") and answers 402 when it does not. No tenant is minted and no device key is issued, which is the same both-halves refusal the unpaid path already makes.
  3. The ongoing door refuses too - src/CcDirector.Gateway/Tenancy/HostedAccessLeaseService.cs. Enrolment is a one-time act; a tenant that already exists re-asks this gate on every hosted request. An account that moves from a hosted plan to a self-host one still has an active, paying row, so the entitlement outcome is legitimately Entitled - it is the plan that refuses, not the payment. Without this line such an account would be served hosted service indefinitely. It denies (402 via the authentication middleware) and deliberately does not revoke device credentials; see the design notes.
  4. A tier constant - a single TierProSelfHost constant added next to the existing TierHosted/TierPro in EntitlementRegistry.cs. That file's behaviour is otherwise untouched: it still passes whatever tier the row carries straight through, unexamined. The money question and the capability question stay separate on purpose.

Design notes - the three decisions worth arguing about

0. How this composes with the fourteen-day Pro trial (merged while this was in flight)

Pull request 2132 landed on main during this work and edits the same two files. This branch was rebased onto it and keeps both behaviours - the trial fold and the plan gate. The interaction is the part worth checking, so it is stated explicitly:

  • EntitlementRegistry.Evaluate now folds a running trial itself and returns tier pro with the trial's end instant. Tier pro carries hosted_gateway in the table, so a trial account still enrols and is still served - the plan gate is invisible to it. That is written intent (issue 2117, owner-approved) and this change does not touch it.
  • The enrolment endpoint's separate act of creating a trial on a first arrival now also stamps tier = TierPro, so a freshly granted trial and an already-running one are ruled on identically rather than the fresh one being judged on the absent paid row's null tier.
  • The gate reads Evaluate rather than LookupBySubject so the outcome and the tier come from the same read of the same row and cannot disagree.

The string trap this creates, and the test that holds it. "pro" is a PREFIX of "pro_selfhost", and "pro" deliberately grants hosted gateway. Any comparison sloppy about where a tier string ends - StartsWith, Contains, a substring or "begins with pro" shortcut - would hand hosted gateway to the exact plan this issue exists to deny, and would look correct doing it. The table matches whole strings by ordinal equality, and ForTier_ProSelfHost_IsNeverTreatedAsThePlainProTier pins it: the two tiers resolve to different scope sets, differing by exactly the hosted gateway scope.

1. The entitlement read does not police plans, and must not start

EntitlementRegistry answers "is there live money for this account". It is tier-agnostic by design and passes the tier through untouched. The refusal therefore lives in the scope table and at the places that authorize a capability - never inside the read. This also keeps the change compatible with the concurrent trial work (pull request 2132), which folds a trial into that same read and returns the literal tier pro.

2. The default is deny, and the null tier is a documented carve-out

An unrecognised tier grants nothing. The two failure directions are not symmetric: refusing a plan we have not taught the Gateway about is visible and reversible in one line, while granting hosted capacity to an unknown plan is invisible - which is the exact bypass this issue exists to close. This mirrors the law EntitlementRegistry already states about subscription states ("a value it does not recognise is NOT entitled").

The one exception is a null tier. The tier column was added to the payment-side table after rows already existed, so a pre-column row reads back null. That is an old hosted row, not an unknown plan, and it has always granted hosted access; folding it into the deny default would lock out established paying customers over a column they predate. It is written as its own entry, with its reason, and pinned by its own test.

3. A plan refusal denies but does not revoke

The cancellation path revokes device credentials (a durable tombstone) when a subscription lapses. A plan refusal deliberately does not. The reason for a plan refusal is a string the payment side writes: a renamed or mistyped plan would otherwise destroy a paying customer's device credentials, and a later correction cannot undo that. The deny is re-evaluated on every request and is sufficient - it produces the same 402 the caller gets for a cancelled subscription. The lease is still overwritten terminal-negative, for the same reason the cancellation branch does it: so a stale positive lease cannot later be ridden into an allow by a failed read.

The tests, and how each one fails on purpose

A test that cannot fail is not proof, so each one below has a stated way to redden it and a paired positive control that stops it passing for the wrong reason (a gate that refused everyone would satisfy every deny assertion while shipping a dead product).

Enrolment - src/CcDirector.Gateway.Tests/HostedEntitlementGateTests.cs

  • A_self_host_plan_is_refused_hosted_gateway_provisioning - the negative control. Reddens if pro_selfhost is given the hosted_gateway scope, or the plan gate is deleted from Enroll: status becomes 200 and a tenant is minted.
  • A_self_host_plan_still_grants_the_artificial_intelligence_features - the paired positive. Reddens if someone "fixes" the refusal by denying the plan everything.
  • An_unknown_plan_is_refused_hosted_gateway_provisioning - the deny default at the door.
  • ForTier_ProSelfHost_IsNeverTreatedAsThePlainProTier - the prefix trap described above: "pro" is a prefix of "pro_selfhost" and grants hosted gateway, so a sloppy comparison would silently undo this whole issue.
  • Pre-existing and still green: An_active_subscription_enrolls, Enrollment_grants_on_any_active_entitlement_regardless_of_tier (hosted / pro / null), Self_host_has_no_gate_at_all (the self-hosted deployment control - no entitlement registry, no gate, unchanged behaviour).

Ongoing access and the table - src/CcDirector.Gateway.Tests/HostedAccessPlanScopeTests.cs (new)

  • AuthorizeAsync_SelfHostPlanOnAnActiveRow_DeniesHostedAccess - the second door. Reddens if the plan branch is removed from HostedAccessLeaseService.
  • AuthorizeAsync_HostedPlanOnAnActiveRow_AllowsHostedAccess - the positive control: an identical row on the hosted plan IS served, so the refusal is aimed at the plan and not at everyone.
  • AuthorizeAsync_SelfHostPlan_DeniesWithoutRevokingDeviceCredentials - pins the deny-but-do-not-tombstone decision.
  • AuthorizeAsync_UnknownPlan_DeniesHostedAccess - the deny default on the ongoing path.
  • AuthorizeAsync_RowPredatingTheTierColumn_AllowsHostedAccess - the null-tier carve-out, so a future edit cannot fold established customers into the deny default unnoticed.
  • Table tests: exact scope set for pro_selfhost; GrantsHostedGateway false for pro_selfhost; still true for hosted / pro / null (the no-regression line); false for an unrecognised tier and for wrong-cased ones (matching is exact, because a tier is a value the payment side writes, not prose to interpret); every paid plan keeps the artificial-intelligence scopes; a blank scope name throws rather than silently answering.

CenCon impact


No architecture drift. No new container, no new dependency, no new persisted data, and
no Entity Framework migration - the entitlements table is website-owned and excluded from
migrations, and it already admits the tier. One new type inside the existing
CcDirector.Gateway Tenancy area.


Security posture: strictly tightened. Every change moves in the deny direction. Nothing
that was permitted before is permitted now except through an explicitly listed plan, and the previously
tier-agnostic provisioning path gained a plan check. (Note: docs/cencon/ in this repository
currently holds only DEVELOPMENT_METHOD.md and proof/ - there is no
architecture_manifest.yaml or security_profile.yaml here to drift, so no CenCon
document required an update.) Nothing personally identifying is logged by the new code paths: the refusal logs
state the reason and never the subject, the email, or the tier value.

Finding for the owner - not fixed here, reported deliberately




Plain tier pro grants hosted gateway today, and this change keeps it that way.
The enrolment gate has always been tier-agnostic, and an existing test
(Enrollment_grants_on_any_active_entitlement_regardless_of_tier) pins pro as
enrolling. Narrowing pro would change shipped, tested behaviour with a billing meaning, so it is
not this issue's call.


The consequence, for whoever owns the trial work: pull request 2132 makes tier pro reachable
with no paid row at all, for fourteen days, on every new account. Combined with the
above, that hands fourteen days of free hosted gateway to every new account. The scope table makes this a
one-line decision if the owner wants it changed - pro simply stops listing
hosted_gateway - but it needs an explicit business decision, not a developer's guess.

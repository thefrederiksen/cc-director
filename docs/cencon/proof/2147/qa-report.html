2. The string trap - is the comparison exact?

This is the mistake that would silently undo the whole issue. "pro" is a prefix of "pro_selfhost", and "pro" deliberately does carry hosted gateway - the fourteen-day trial on main grants exactly that tier. Any comparison sloppy about where a tier string ends would hand hosted gateway to the one plan this issue exists to deny, and would look correct doing it.

The code was read, not summarised. EntitlementScopes.ByTier is a Dictionary<string, IReadOnlySet<string>> constructed with StringComparer.Ordinal, and the lookup is a single ByTier.TryGetValue(tier.Trim(), out var scopes). That is whole-string ordinal equality. There is no StartsWith, no Contains, no substring arithmetic and no case-insensitive comparer anywhere in the file. The only normalisation is Trim() on surrounding whitespace, which cannot turn one tier into another.

The test that pins it exists - EntitlementScopeTableTests.ForTier_ProSelfHost_IsNeverTreatedAsThePlainProTier. It asserts that "pro" really is a prefix of "pro_selfhost" (so the trap is real and not hypothetical), that the two tiers resolve to different scope sets, and that the difference is exactly the hosted gateway scope. Case sloppiness is pinned separately by GrantsHostedGateway_AnUnrecognisedTier_IsFalse with "PRO_SELFHOST" and "Hosted".

Reading a test is not proof that it works, so it was made to fail - see sabotage D below, where replacing the exact lookup with a prefix and case-insensitive match reddens that test and seven others.

4. The deny default - a guard has two failure directions

Checked in both directions, not just the one the issue names.

  • Unknown tier is DENIED. ForTier returns the empty set for any tier string not in the table, so GrantsHostedGateway is false. Enforced at both doors and pinned at both: An_unknown_plan_is_refused_hosted_gateway_provisioning (enrolment, 402 with nothing given away) and AuthorizeAsync_UnknownPlan_DeniesHostedAccess (ongoing). Both reddened under sabotage B and C respectively, so both are load bearing.
  • The tiers that already granted it still do. hosted, pro and a null tier all still grant hosted gateway (GrantsHostedGateway_TheTiersThatAlreadyGrantedIt_StillDo), so the new table does not quietly take hosted access away from an existing paying customer. The null carve-out is the pre-column row and is written as its own documented entry rather than hidden in a default.
  • Self-host deployments are untouched. A null entitlement registry means no gate at all, which is the deployment that has no billing. That control is still green.

One observation, not a defect

A tier column holding only whitespace is treated as null and therefore grants hosted gateway. That is the documented pre-column carve-out and is correct for the rows it exists to protect; it is recorded here only so the behaviour is on the record. The payment side writes the literal string pro_selfhost, which the Gateway matches exactly, so nothing about the self-host plan depends on this path.

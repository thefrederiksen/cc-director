A real test-isolation bug I found and fixed (in the test harness)

My first broad run showed two existing tests failing only when my new test class ran in parallel. Root cause: these tests place the persist file directly in Path.GetTempPath(), so they all share one TEMP/voice-audio durable cache dir — a session id one test writes is loaded by another test's fresh service constructor (LoadReadyAudio). My new tests write the same sid-1 concurrently. Fix: my tests use a unique subdirectory per test, so the cache dir never collides. After the fix the full set is green (263/0). I did not alter the existing tests (their latent sharing is pre-existing and safe sequentially); I only kept my additions from contaminating them.

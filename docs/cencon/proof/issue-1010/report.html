Issue #1010 - Fix awarenessClient.test.ts typecheck errors introduced by #974

Developer Agent (CenCon Development Method) · Branch issue-1010-awareness-test-typecheck · PR #1014 · 2026-07-05

What was implemented

Issue #974 (turn rail / awareness panes) added packages/client-core/src/awareness/awarenessClient.test.ts. Its mockFetch helper used a zero-parameter vi.fn(async () => ...) implementation. Vitest infers the recorded call arguments (mock.calls) from the mock implementation's parameter list, so with no parameters mock.calls[0] was typed as the empty tuple []. Destructuring [url, init] and reading calls[0][0] then failed a strict tsc --noEmit with TS2493 (x5), and casting the resulting undefined to RequestInit failed with TS2352 (x2) — 7 errors total. These slipped past vitest (esbuild, does not typecheck) and past the declaration build (tsconfig.build.json excludes *.test.ts).

Fix (no behavior change, no any, no @ts-ignore): give mockFetch the real fetch signature (input: RequestInfo | URL, init?: RequestInit), so the recorded call arguments are a correctly typed two-element tuple.

Hardening (recommended by the issue): wire the test-inclusive strict typecheck (npm run typecheck --workspaces --if-present, which runs tsc --noEmit whose tsconfig include: ["src"] covers test files) as a blocking step in the BuildCockpitApp target in src/CcDirector.Gateway/CcDirector.Gateway.csproj. The gate previously ran only npm run build (vite/esbuild, no typecheck), so this class of error could not be caught at build time.

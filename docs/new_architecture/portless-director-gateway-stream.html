Portless Director: one outbound stream to the Gateway

Status: CANDIDATE -- UNDER CONSIDERATION. Not decided. This records a target model we are actively brainstorming, so we can see it whole and find the holes. Nothing here is built.

Date: 2026-07-08

Relationship to the state-and-color document: that document decided the Director is a sensor and the Gateway is the single interpreter (one fold). This document proposes HOW the Director and Gateway talk so that rule holds even across machines and Gateway restarts. It replaces the current three-channel model (register + 15s heartbeat + doorbell) plus the on-demand fan-out pull, with a single persistent connection the Director dials out to the Gateway.

The one idea

The Director opens exactly one connection -- outbound -- to the Gateway, and keeps it open. Everything flows over it: raw state pushes up, commands and requests flow down, on-demand requests work in both directions, and terminal bytes ride outbound byte streams the Director dials on demand. The Director exposes NO network-facing ports. The Gateway is the only reachable host in the system.

Because the Director dials out, it needs no inbound firewall port, no port-forward, and no per-machine tailnet address. It works behind any NAT or firewall that allows outbound HTTPS -- home, corporate, cellular, anywhere.

The invariants (these are the "musts")

  1. The Director dials the Gateway. The Gateway never dials the Director. This is the whole point; it is what makes the Director portless.
  2. No Director ever talks to another Director. All cross-session messaging, fleet comms, and remote viewing/control is relayed by the Gateway. If any Director-to-Director path survived, something would still need to be reachable and the benefit collapses.
  3. All remote access goes through the Gateway. A phone or another machine can only reach a Director by way of the Gateway.
  4. The Director keeps a loopback-only API. 127.0.0.1 only, for the local agent, the cc-* CLI tools, and the Director's own window. This exposes no network port, so it does not violate portless -- and it means local work never depends on the Gateway being up.
  5. Who-initiates is not who-can-ask. One Director-initiated connection still carries requests in both directions. The Gateway can ask the Director for history on demand over the open stream; portless forbids only a new inbound connection, not the request/response pattern.

The picture

The single reading: one outbound stream carries everything; the Director opens no ports; the Gateway is the only door. A dropped stream is normal -- the Director redials and re-seeds. When the stream is down the desktop keeps working locally on dumb colors; remote access is simply unavailable until it is back.

What collapses into the stream

Everything that is a separate Director-Gateway mechanism today becomes one channel:

Today Under this model
Register on start (HTTP) Stream connect (with auth in the handshake)
Heartbeat every 15s (HTTP push) Stream keepalive ping + periodic full-snapshot reseed
Doorbell on change (HTTP push, best-effort) Delta pushed up the stream
Gateway fan-out PULL of each Director /sessions on client poll Gateway serves its own in-memory model; no fan-out
Assessed-state down-push (HTTP into the Director) Message down the stream
Commands: Gateway -> Director HTTP (needs inbound port) Message down the stream (no inbound port)
Terminal bytes: browser -> Director direct (via tailnet) Director-dialed outbound byte stream, relayed by the Gateway
History/turns: Gateway PULLS Director on demand (inbound) Request down the stream; Director answers up it

Recovery: reconnect is the same path as first connect

The Director is the source of truth; the Gateway is a disposable derived cache. So the Gateway never "reacquires" -- the Director re-asserts. Every attach (first time or thousandth reconnect) begins by sending a full snapshot of every session's current facts; then deltas flow. No diffing, no gap replay. A monotonic epoch per attach lets the Gateway drop any stale message from a dying connection. Nothing is lost because the durable truth (terminal buffer, transcript files, raw facts) never left the Director.

Consequences we accept, eyes open

  • The Gateway becomes a single point of failure for REMOTE access. With no direct path, when the Gateway is down no phone or other machine can reach a Director at all. The desktop keeps working locally (loopback + dumb colors). This raises the value of Gateway availability later.
  • The Gateway enters the byte data path. Bytes go Director -> Gateway -> browser instead of browser-direct. Measured load is small (single-digit KB/s per watched session), but the Gateway now relays bytes, not just metadata.
  • Local fleet comms now depend on the Gateway. Session-to-session messaging routes local agent -> loopback -> stream -> Gateway -> target Director. A local command to another session needs the Gateway up.

Connection status in the Director window

The Director already shows "connected to the Gateway." Under this model that indicator becomes load-bearing: green when the stream is healthy, yellow while reconnecting, red when the stream is down (and the rail has fallen back to local dumb colors). It is the user's single signal for "is remote access working right now."

Session State and Color Architecture

Date: 2026-07-08

Verified against: working tree on 2026-07-08 (main). Code is referenced by symbol name; verify before acting.

Audience: Anyone who touches session status, activity state, or color in the Director, the Gateway, the Cockpit, or the mobile client. Read this before adding any state or color rule anywhere.

The state map (at a glance)

Where every piece of state comes from, where it is decided, and how a change reaches each screen. State converges on the Gateway, is folded exactly once, and fans back out to the viewers. Commands travel the other way: any client sends a command up to the Gateway, which is the only place state actually changes.

The one-line reading: the Director senses, the Gateway decides, the viewers render. A change is instant for whoever made it (the command echoes the new state back) and for the desktop rail (a down-push), and lands within one poll for the browsers. Terminal bytes are a separate fast path -- a direct WebSocket from the Director to whichever viewer has the session open -- and never pass through the fold.

1. The one rule (DECIDED)

The cc-director holds zero authority over interpreted session state and color. It is a sensor, not an interpreter. It observes raw terminal activity and reports it as a fact. The Gateway is the single master of interpreted state and color. Every client renders the Gateway's field; no client re-derives it, including the desktop app when a Gateway is connected.

This is the settled decision. The rest of the document explains why it is safe, what "sensor" means precisely, and what has to change to get there.

2. Sensor versus interpreter

The confusion in the current code comes from conflating two different things under the word "state." Separate them and every ownership question answers itself.

A fact is something only the observer can know. For example: "bytes came out of this terminal at time T," or "this terminal has been silent since time T." Only the process that holds the live terminal can know these. Reporting a fact is not an act of authority; it is a sensor reading.

An interpretation is a judgment layered on top of facts. For example: "silent for 10 seconds, and not being briefed, and not transcribing, and not preparing voice, therefore this session NEEDS YOU, therefore paint it red." Or: "this session is parked on its own background build, therefore paint it purple, not red."

An interpretation needs inputs beyond the byte stream (briefing state, voice readiness, on-hold, transcribing, sub-agent relationships) and it encodes policy. It belongs to the layer that has all those inputs and owns the policy: the Gateway.

Restated in plain terms: "when keystrokes happen, the Director just lets the Gateway know, and the Gateway can do anything." The keystroke or byte notification is the sensor reading. Agreed and adopted.

3. Why the sensor must stay in the Director

The raw signal is a function of the live terminal byte stream and the rendered terminal grid, not a simple "a key was pressed." The TerminalStateDetector today:

  • flags Working the instant a byte arrives, and re-arms an idle countdown on every byte;
  • distinguishes a real body change from a footer-only repaint;
  • suppresses spinner and animation frames so a spinning session does not read as "working forever";
  • applies a brand-new grace window so a fresh session does not flash blue before it has done anything.

That is genuine raw-signal plumbing that must live next to the bytes. Moving it to the Gateway would mean streaming every byte of every terminal on every machine to the Gateway continuously, which is exactly the coupling this architecture removes.

So the sensor is local. But it emits a fact (Working or Waiting, plus a timestamp), never a color and never "needs you."

4. Where the silence threshold lives (CONFIRM)

Question: the "silent for 10 seconds, therefore waiting" threshold. Does the Director own it, or does the Gateway?

Recommendation: detection runs in the Director (it must, because the bytes are there), but the threshold is a configuration value with a local default of 10 seconds that the Gateway can override by pushing config down.

Why: this gives "the Gateway can change the rule fleet-wide without a Director release," which serves the goal that the Director changes as rarely as possible, while keeping the sensor able to run standalone with a sane default. Changing 10 seconds to 5 seconds becomes a Gateway config change, not a Director code change and redeploy.

What we do not do: forward every raw byte heartbeat to the Gateway and have the Gateway run per-session silence timers for the whole fleet. That adds Gateway-side timing state and a constant heartbeat for no benefit the config-override approach does not already give us.

5. The target flow: one direction, one fold

DIRECTOR  (sensor - the only place that sees the bytes)
           terminal bytes  ->  ActivityState fact: Working | Waiting + sinceTimestamp
           plus the raw local facts it already knows:
             isBrandNew, controllerSessionId, isBackgroundRunning, isExited
                |
                |  reports facts up (no color, no interpretation)
                v
        GATEWAY  (interpreter - the single master of state and color)
           raw ActivityState fact
             + briefing state            (Gateway brain owns this)
             + voice generating / ready  (Gateway WingmanVoiceService owns this)
             + transcribing              (Gateway owns this)
             + on-hold, sub-agent support, background, brand-new
                =>  ONE fold  =>  EffectiveColor + TriageBucket + StateLabel
                |
                |  stamps the computed fields on SessionDto, sends down
                v
        CLIENTS  (Cockpit, mobile, and the desktop rail when connected)
           render EffectiveColor / TriageBucket / StateLabel. No re-derivation anywhere.

The defining property: state and color flow in one direction only, and the fold happens exactly once, at the Gateway. Contrast this with the current circular flow in section 9.

6. What the Director stops doing

Under this rule the following moves off the Director:

  • Delete the overlay fold. SessionStatusWingman.ResolveActivityColor currently folds seven overlays (transcribing, briefing, explaining, background, brand-new, supporting, voice-preparing) into Session.StatusColor. That fold is deleted from the Director. It exists once, at the Gateway.
  • Stop writing an interpreted status color. The Director reports the raw ActivityState fact and the underlying raw facts (isBrandNew, controllerSessionId, isBackgroundRunning). It does not decide what color those add up to.
  • Stop consuming pushed-down interpreted state to re-fold it. The Gateway no longer pushes briefing, voice, or assessed state down into the Director so the Director can fold it into a color. That downward re-fold leg is removed; it is the loop described in section 9.

What the Director keeps: the TerminalStateDetector sensor, the raw fact it emits, and (only for the standalone fallback in section 8) a trivial local color map.

7. The color scheme

This is the full set of colors and their meanings, in precedence order (first match wins). Today this logic is split across SessionOrdering.EffectiveColor and SessionStatusWingman.ResolveActivityColor. The target is that it lives once, at the Gateway.

Order Color Meaning Driven by
1 Grey #6B7280 On hold or parked by the user or agent; also an exited process. Sinks to the bottom of triage. OnHold, or Exited
2 Orange #F97316 Busy receiving input that must not be interrupted: a dictated utterance is transcribing, or a user-requested "explain" deep dive is running. Shown regardless of underlying activity so no one else types into the session. Transcribing, or briefing state Explaining
3 Yellow #F59E0B The Wingman is reading a finished turn (briefing in flight), or a voice-mode session is preparing its spoken audio. We do not yet know whether it needs you. briefing state Briefing at a turn-end, or voice preparing
4 Purple #A855F7 The session is parked on its own background task (a build, a running shell), not on the user. IsBackgroundRunning at a turn-end
5 Slate #64748B A sub-agent being driven by another session; it recedes so the operator is not nagged. Red still breaks through this. IsControlled and the controller is alive
6 Green #22C55E Ready: a brand-new session sitting at its prompt, available, not yet having taken a turn. IsBrandNew at a turn-end
7 Blue #3B82F6 Working: the terminal is producing output. raw ActivityState = Working
8 Red #F14C4C Needs you: the terminal has been silent past the threshold with none of the overlays above applying. The only color that drives the "needs you first" triage bucket. raw ActivityState = Waiting

Two invariants worth stating:

  • Red is a verdict, not a raw reading. A session that has gone silent is not automatically red; it is red only after the overlays above have had their say. This is why the fold must be atomic and in one place: computing it in pieces is what let a session flip into "needs you" mid-brief and back out.
  • Red breaks through the slate "supporting" recede so a genuinely blocked sub-agent still surfaces.

8. The standalone fallback (CONFIRM)

The desktop Director app is the permanent fallback and must paint something when no Gateway is present or reachable. The smart overlays (briefing, voice, transcribing) do not even exist without the Gateway, so there is nothing to fold.

Recommendation: with no Gateway, the desktop app applies one deliberately dumb local map to the raw sensor fact: Working becomes blue, Waiting becomes red, Exited becomes grey. No overlays, ever.

This is not a violation of section 1. It is a last-resort render of the one fact the app can see when there is no brain to ask, not a policy layer. When a Gateway is connected, the desktop rail renders the Gateway's EffectiveColor field like every other client (render, never recompute), so the desktop and the Cockpit always agree.

9. Current violation inventory (2026-07-08)

The code today disagrees with the target in three connected ways.

Three folds, not one. The same overlay logic is computed in three places:

  1. SessionStatusWingman.ResolveActivityColor (Director) folds about seven overlays into the session status color.
  2. SessionOrdering.EffectiveColor (Gateway) re-derives the orange and yellow overlays on top of the Director's already-folded status color, and writes EffectiveColor.
  3. packages/client-core/src/sessions/ordering.ts (TypeScript) re-derives the same thing again for the Cockpit, plus inline bypasses in FleetMapView, ExesView, and DirectorDetailView.

A circular data flow. The Gateway pushes briefing, transcribing, voice, and assessed state down into the Director; the Director folds them into the status color; that goes up to the Gateway; the Gateway re-folds into EffectiveColor; that goes down to clients; the client re-folds again. State makes a full loop and is interpreted at every hop.

A contradiction that generates bugs. SessionOrdering.EffectiveColor documents its assumption as "the Director stamps the raw status color (it no longer knows about briefing)." But SessionStatusWingman does fold briefing, and six other overlays, into the status color. The two layers disagree about whether the status color is raw or already cooked. That exact ambiguity produced the "stuck orange" and "stuck yellow" wedges: the same rule had to be fixed in C# and in TypeScript at the same time.

The target (sections 1-6) removes all three: one fold, at the Gateway; one direction of flow; and the interpreted status color ceases to exist as a Director field, because the Director emits only the raw fact.

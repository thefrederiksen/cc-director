New rule

Say what you want to happen.

YOU

If a provider is down or rate limiting me, just wait it out and pick up again. Only bother me if it's still stuck after an hour.

DT

Got it. Three things I need to pin down, because guessing them would make this rule do something you did not ask for.

1. These screens usually name a time to retry - "try again in 4 minutes", or a reset hour. Should I wait for the time it names, or a fixed gap?

2. When the wait is over, do I just say "continue", or should I be more specific about what it was doing?

3. Your hour - is that an hour from the first failure, or an hour of me retrying?

YOU

Use the time it gives if there is one, otherwise five minutes. Just say continue. And an hour from when it first broke.

DT

Here is the rule.

I wake up when the screen contains rate limit, overloaded, try again, 503, 529 or temporarily. Otherwise this rule costs nothing.

Then I check that the session really has stopped on a provider problem rather than just mentioning one - an agent discussing rate limits in its own output is not a session that is stuck.

I read the retry time off the screen and hand it to DevThrottle's own work-out-the-wait check rather than doing the sum myself, because "back at 5pm" versus "in 4 minutes" versus a reset timestamp is arithmetic, and arithmetic is where I would make a quiet mistake. I choose the check and supply the values; I do not write it.

Then I snooze the session for that long, and when it wakes I type continue.

If it is still failing an hour after the first failure I stop retrying and wake you.

Starting in dry run. I will tell you what I would have done, and type nothing, until you promote it.

Permission prompts inside the repo

Dry run   Would have acted 6 times, declined twice.

What it worked out from that

Regenerated whenever you change the sentence. Editable, but you should rarely need to.

Do you want to permission allow yes / no proceed?
Is this path inside this directory? built in

One of DevThrottle's own checks, written and reviewed by us and shipped like any other feature. It resolves the path first, so .. cannot walk out of the repo and a symlink cannot pretend to be inside. The rule supplies the two values; it does not supply the check.

You cannot edit this, and neither can the model. It picks which check to use and what to pass it. Nothing it writes is ever executed.

Limits

Dry run · at most once every 2 minutes per session · at most 40 a day per session · only when the session is stopped and waiting.

The two it declined - worth reading before promoting

Yesterday 22:14 - asked to write to C:\Users\soren\.ssh\config. Outside the repo, so it left it and flagged you.
Today 08:02 - asked to run a script whose path resolved outside the repo through ... Declined and said so.

Your question: for the model switch, is that Python or just a prompt?

Just a prompt. No code at all. Every step of that rule is reading and typing, which is what a model is for:

  • "Has this session run out of allowance?" - judgement about English that varies by provider. A model.
  • "Type /model opus" - fixed text you supplied. Nothing to compute.
  • "A confirmation appeared - deal with it" - reading a picker whose wording and option order vary. A model again; a hardcoded "press 1" is exactly the brittleness we are moving away from.
  • "Carry on" - fixed text.

There is nothing in it that has to be exact rather than understood, so there is nothing for code to do.

So when does it use an exact check instead of judgement?

When being exactly right matters more than being able to read. Three tests, and a rule reaches for a built-in check if any is true:

  • Arithmetic. "Back at 5pm" into a wait in seconds, across a timezone. Models are unreliable at this in a way that is quiet.
  • Containment and comparison. Is this path inside that directory? A model reading /repo/../etc/passwd may well say "inside the repo" - it looks like it is. Three lines of code answer it correctly every time.
  • Anything a wrong answer makes unsafe. If getting it subtly wrong grants something it should not, it does not go to judgement.

The line, in one sentence: the model decides, and a built-in check is used wherever being exactly right matters more than being able to read. You never choose which - it picks, and it tells you which it picked and why.

Nothing generated ever runs on the Gateway

The obvious version of this feature has the model write a bit of code and the server run it. That was the earlier draft of this page and it was wrong - it would mean running code we did not write, on our server, derived from what a customer typed. No sandbox makes that a good trade for a feature whose job is already to type into people's sessions.

So nothing generated runs. DevThrottle ships a small set of checks we wrote and reviewed - is this path inside that directory, how long until this retry time, how long since this first failed. The model's job is to pick one and supply the values. What gets stored in the rule is a call - a name and its arguments, validated against that check's signature before it is used. Never a program, an expression, or a snippet.

That removes the problem rather than containing it. There is no interpreter, so there is no escape to find and no resource limit to tune. The worst a wrong choice can do is pass wrong values to a function that already has its own unit tests - a wrong answer, not a compromised server. And no user ever writes or edits code here: the only thing anyone types is English.

The cost, which is real: some rules will not be expressible. When an instruction needs an exactness no built-in check provides, it says so and either builds the rule without that part or declines - and if the gap is worth closing, we add a check, which is an ordinary product change with human review. What it must never do is route around the gap with a general-purpose check that takes an arbitrary pattern or expression. That is the interpreter coming back under a different name.

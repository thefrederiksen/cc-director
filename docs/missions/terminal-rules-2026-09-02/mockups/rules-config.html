Rules - screens, version 2

Rebuilt after the owner's redesign (ruling 14). Version 1 was a form: a description you wrote yourself, trigger words you chose yourself, and an action picked from a dropdown of six. Proposal only - nothing here is built.

What changed. A rule is no longer a form. It is a standing instruction you give in plain English, that an agent works out and then carries out. You do not write a matching expression, you do not choose trigger words, and you are not limited to six actions.

1. Your rules, as the sentences you actually said

Each rule is shown as the instruction you gave. What the agent derived from it - the trigger words that keep it cheap, the plan - is there if you want it, folded away if you do not.

New rule

Tell it what you want to happen. It will ask if anything is unclear.

YOU

If a session is asking me for permission to do something inside the repo it is already working in, just say yes. If it wants to touch anything outside that, don't - leave it and tell me.

DT

Understood. Here is what I will do.

I will watch for a session stopped on a permission question - the kind that is waiting for a yes or no before it can carry on.

When I see one I will read what it is actually asking for, work out whether the path or the action is inside the repository that session is working in, and answer yes if it is. If it is outside, or I cannot tell which, I will leave it alone and flag it for you.

To keep it cheap I will only look properly when the screen contains one of: Do you want to, permission, allow, yes / no. Otherwise the rule costs nothing.

One thing I want to check: if it is asking to run a command rather than touch a file - a build, a test, a script - do you want that treated the same way?

YOU

Yes, same thing. If it runs inside the repo it's fine.

DT

Noted - commands judged by where they run, same test.

And when I am not sure, I stop. I will never guess a yes.

I will start in dry run: I will tell you what I would have done each time, and type nothing, until you say go live.

What I am still unsure about

  • What stops an agent doing too much. The old design claimed the six-item dropdown was the limit. That was never true - typing into a coding session is already unbounded, because the session does whatever the text says. The real limits are: scope, dry run first, a hard ceiling on how often, and a full record. Those are honest. There is no vocabulary that makes this safe, and pretending otherwise was worse than saying so.
  • Whether "carry on with what you were doing" is one instruction or two. Recovering a session and resuming its work are different acts, and the second one may deserve its own consent.
  • Whether a rule should be able to say "ask me first". A middle state between dry run and live - it acts, but only after a push notification you tap. Probably yes.
  • What the undo story is. Some actions cannot be taken back. The record says what happened; it does not reverse it. That gap deserves a real answer rather than a button.

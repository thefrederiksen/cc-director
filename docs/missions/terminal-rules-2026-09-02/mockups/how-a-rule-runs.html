How a rule is created, and how it actually runs

Answering four questions: what a rule can see, who decides, who types, and how you make one. Proposal - none of this is built yet. Where something is not settled, it says so.

The short answer to "is it a language model or code?"

It is both, and the split is the whole design. A model that could type would be a model that could invent an instruction you never gave.

Ordinary code decides whether to ask. A small model decides which rule matches. Ordinary code does the typing.

The model is asked one narrow question and can only answer with the name of one of your rules, or "none". It never produces the text that gets typed. Every character that reaches your session comes from the rule you wrote, exactly as you wrote it.

(It is C#, not Python - it lives in the Gateway, which is a .NET service. Nothing here runs on your machine.)

The path, step by step

This runs when a session STOPS - the moment it goes from working to waiting. Not continuously, and never mid-turn.

CODE
1. A session stops working Its screen is captured and pushed to the Gateway - the thing phase 0 just built. No rule is involved yet.
↓
CODE
2. Is this screen even worth looking at? Has it changed since last time? Is the session actually idle? Has this rule already fired here, or hit its daily limit? Any "no" stops here.
↓
CODE
3. Do any of your watch-words appear? Plain text search. If a rule lists words and none are on the screen, that rule is dropped without ever asking the model. This is the cost control - it is why having rules costs nothing on the thousands of ordinary screens.
↓
CODE
Nothing survived - stop. This is the normal outcome. Free. No model was asked. Most turn-ends end here.
↓
MODEL
4. One question, once: which of these rules fits this screen? The model gets the screen and the surviving rules' descriptions. It answers with one rule's name, or "none". One call covers all your rules - not one call per rule - so ten rules cost the same as one.
↓
CODE
5. Look at the screen again, right now Between the model answering and anything being typed, the screen is re-read. If it changed, or a menu appeared that was not expected, the action is abandoned rather than pressed into something new.
↓
CODE
6. Type your text, verbatim The exact characters from your rule - /model opus - into the composer, the same way the text box on your phone does it. Then record what happened: the screen, the verdict, the keystroke.

What a rule can see

Always the terminal screen. That was raised as an open question and the owner settled it on 2 September - see the box below the table.

Settled 2 September: the screen is the only input

This was raised as an open question - whether a rule should also be able to trigger on things that never appear on a screen, like a session stuck for an hour or burning money. The owner's answer: "Let's leave it at just the terminal for now."

So a rule's condition is a description of a terminal screen and nothing else. The other rows above are kept rather than deleted, because knowing they were considered and deferred is worth more than a shorter table.

Deferred, not rejected - and it will not be pre-built behind an abstraction "ready for later". A condition type with one possible value is surface a reviewer has to read for behaviour that cannot happen. Build the narrow thing properly; widening a small clean thing later is ordinary work.

How you create one

Three ways in, all landing on the same thing.

  1. From a screen that already stopped a session. The main way. You are looking at the stored screen, you press "Make a rule from this", and the model turns that screen into a first-draft description in plain English. You edit it, choose what to do, save. You never have to guess what the terminal said, because it is stored in front of you.
  2. From scratch. An empty rule. You write the description yourself. Useful when you know the situation but have not hit it yet.
  3. From a starter rule. Ready-made ones for the situations everybody meets - out of allowance, provider down, waiting on a permission prompt. You pick the action and the fallback model; the description is already written.

Whichever way in, a new rule starts in dry run: it reports what it would have done and types nothing. You promote it to live once you have watched it be right. That is deliberate - the first time a rule presses a key in your work should not be the first time you have seen it make a decision.

What you write, in full

The description - the only part the model reads

Plain English, in your words. "The agent says it has run out of usage or credits for the model it is running, and offers switching models." The model judges the screen against this sentence. Wording that varies between providers still matches, which a keyword search cannot manage.

The watch-words - optional, and purely about cost

If you list them and none appear, the model is never asked. Leave it empty and every screen gets judged, which works and costs more. This is not a filter you have to get right; getting it wrong only costs money, never correctness.

The action - what a person would have typed

Switch model, type this text, notify me, snooze then continue, stop the session, or flag it and wait. Nothing else is offered, and there is no box where you can put a shell command.

The limits - not optional

How long before it may act on the same session again, how many times a day, and whether it is live or in dry run. A rule presses keys into running work; it does not get to do that without a ceiling.

The three things this design refuses to do

  • The model never writes what gets typed. It picks one of your rules by name, or none. Every keystroke is yours, verbatim. This is the same rule dictation lives under, for the same reason.
  • Rules never run commands. Every action is something you could have typed into that session yourself. There is no escape hatch, deliberately.
  • Nothing acts on a session that is working. Only on one that has stopped and is waiting - and only after looking at the screen a second time, immediately before pressing anything.

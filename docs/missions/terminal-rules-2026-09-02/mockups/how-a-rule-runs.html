How a rule is made, and how it actually runs

Version 2, after the owner's redesign. A rule is a standing instruction you give in English, that an agent works out and then carries out. Proposal - none of it is built.

What changed, and why version 1 was wrong

Version 1: you wrote a matching description, you chose the trigger words, and you picked an action from a dropdown of six. A model was used for one narrow thing - deciding which of your rules a screen matched - and was explicitly forbidden from composing what to type.

The part that was not just rigid but dishonest

Version 1 said: "only things a person could have typed into that session - there is no way to run a command of your own", as if the six-item list were a safety boundary.

It never was. Typing into a coding agent is already unbounded - the session does whatever the typed text asks it to. The dropdown bought the appearance of a limit and none of the substance. A design whose safety story is false is worse than one that states the real bound, because people trust it.

So what actually bounds it?

The honest answer, since the action list is not a bound and never was.

Six real limits

1. Scope. A rule only ever touches sessions you chose - this agent, this repo, this machine, this mission. Enforced in code, not judgement.

2. Dry run first, always. A new rule reports and types nothing until you promote it. This is the big one: it puts you between the instruction and its first real use.

3. A ceiling. A cooldown and a daily cap, per rule per session, both required. An agent in a loop is the worst tail risk there is, and the cap is what makes it finite.

4. Idle only, and re-read before acting.

5. A full record of every firing - kept, readable, and the reason it is safe to leave running overnight.

6. Your instruction is the authority. The agent carries out what you wrote. It does not invent goals, widen its own scope, edit its own rule, or write new rules.

Limit 6 is the one that would decay quietly

The others fail loudly - a scope bug sends a keystroke somewhere visible, a ceiling bug shows up as a burst. An agent gradually doing a bit more than it was told looks like an agent being helpful, right up until it does not.

So that is the one the tests are written against: given an instruction and a screen it does not cover, the agent declines and records why. A rule that never declines has not been shown to have a boundary.

What this does not change

  • The screen is still the only input. Your ruling. Waiting time, spend and machine state stay deferred.
  • Dictation is untouched. The rule that your spoken words reach the agent unaltered is absolute and has nothing to do with this. That rule exists so YOUR words are not rewritten; a rule here is an instruction you gave on purpose, and carrying it out is the whole job.
  • Nothing runs on your machine. This is the Gateway, in C#, with the agent called from there.

Still open

  • A middle state between dry run and live - it acts, but only after you tap a notification. Probably worth having.
  • "Carry on with what you were doing" may be two instructions, not one: recovering a session and resuming its work are different acts.
  • Undo. Some actions cannot be taken back. The record says what happened; it does not reverse it, and that gap deserves a real answer.

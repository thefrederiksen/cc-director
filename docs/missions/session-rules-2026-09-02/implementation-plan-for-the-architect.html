Session Rules - the implementation plan

Everything needed to hand this to an Architect and get back a working, tested rules engine with a QA report. What the feature is, what exists today, the architecture, the phases in order, the screens, and the three scenarios the QA report must prove with screenshots.

1. The goal, in the owner's words

"The user should be able to set up rules: when you see this message in the terminal window, do this. We need a rule language. And we need a small language model involved in these decisions. This would be a massively beneficial new feature for making our agents more autonomous."

The measure of done is not that the machinery is elegant. It is that the things that actually stop the owner's sessions get handled without him - a usage limit at 3am, a provider outage that killed every session, a permission prompt he would always say yes to. The QA report proves exactly those, on real screens.

Two rulings that bound the whole design, settled with the owner and not to be re-litigated:

  • The terminal screen is the only input to the decision. A rule wakes only when a session goes idle, and reads only that session's screen.
  • No generated code ever runs. A rule holds the NAME of a reviewed check plus argument values - never a program, a script, or "a little bit of Python". There is no interpreter, so there is nothing to sandbox. Widening the checks is a code review and a release.

The one measured fact that reorders everything. The run-time model call asks a REASONING model to write ~600 characters of JSON and times out about one time in three. Measured: the same work on the fast model (Qwen2.5-72B) as a yes/no question returns in 0.4 seconds, every time, and answered all six screens - including three that carry the trigger words and must still be declined - correctly. That is why Phase 1 comes first among the builds.

3. Architecture

Two separate model calls with opposite requirements, one store, and a client surface that is identical whether driven from the Cockpit or from Claude Code.

The client is dumb; the Gateway owns everything. The Cockpit page and the command line are two thin clients of the same four routes. The Gateway decides, scopes, validates, and records; the Director only ever types. This is why "set up a rule from Claude Code" is the same feature as "set up a rule on the page" - and why the built-in page never has to be the clever one.

4. What a rule can do - and cannot

Smaller than the word "rule" suggests. When it fires it does exactly one thing: types one piece of text into one idle session. Everything else is deciding whether to.

It can see (four inputs)

  • screen_text - the terminal tail
  • session_repository_path
  • now - the clock
  • first_failure - when trouble began

Plus the agent it runs, used to scope and to read the screen - never to read a file, the network, or another session.

It can decide with (five checks)

  • matches_any(text, terms)
  • is_path_inside(target, root)
  • retry_delay_from(screen, now)
  • elapsed_since(first, now)
  • extract_first(screen, kind)

Stored as a NAME plus values, checked against the real signature before it can be written. A sixth is a release, not a setting.

The blast radius is the session, not the server. A rule's own powers are tiny, but it types into a coding agent, and a coding agent is unbounded - that is the settled ruling, and it is why "which actions are allowed" was never the boundary. The real boundary is scope, ceilings, idle-only, dry-run, and who promoted. That is where the safety lives, and all of it is on the Gateway.

6. The phases

Ordered so each one is independently valuable and mergeable, and so nothing later is built on an unproven earlier step. Phase 0 comes first because it is what tells us the rest works.

Phase 0
The test harness of real screens
Nothing else is trusted until this exists.

A corpus of REAL captured terminal screens with the right answer written down, and a runner that puts each through the real engine. Half must be negatives - the trigger words present, the answer still "decline" (words in docs being read, in code just written, in a report about another session). Screens come from a capture command and, once Phase 2 lands, from what the engine already reads on every turn.

Acceptance
The runner reports, per model, per case: the answer, whether it was right, the time - and the count of wrong answers on negatives, which is the number that matters. It runs against the real engine, not a copy. At least 20 real cases, at least half negative.
Phase 1
Make the run-time call reliable
Fixes the ~1-in-3 timeout that makes live rules unreliable today.

Move the evaluating call to the fast model and a yes/no shape: the text to type was already decided and approved at authoring time, so the run-time call only has to answer "is this that situation". Measured at 0.4s. Keep the smart model for authoring, where a person waits and quality matters.

Acceptance
Against the Phase 0 harness: zero timeouts across 20+ cases; zero wrong answers on the negatives (a false "act" is the unacceptable failure); the negative control (a rule declining a screen that carries its own trigger words) passes on the fast model. The text typed is the authored text, verbatim - nothing composed at run time.
Phase 2
The clock
The owner's most common case: limit at 3am, everything sitting until morning.

A rule can say "not now - come back at 11:50pm", and something wakes the stopped session then. Today the only trigger is working-to-idle, so a session parked overnight is never looked at again. Use retry_delay_from (already shipped) to read the reset time, and DevThrottle's existing schedule machinery to re-evaluate. Ceilings still bound it.

Acceptance
A rule scheduled to re-look fires within a small window of the stated time, on a real session, end to end. A limit that never clears does not loop past the daily cap. The firing record shows the wait and the wake. Proven on a real (or faithfully simulated) limit screen - not only in the unit suite.
Phase 3
The page agent that fetches the terminal itself
The conversation in the mockup - ask which session, read it, propose.

The authoring call becomes a tool-use loop: the model can list sessions and read a screen, show it, and then propose. The grounding, scope, and agent handling all already exist - this is the loop that lets the page reach them without a person pasting a screen. The command line already reaches them via --session, so this is the page catching up to the API.

Acceptance
On the page, from "set up a rule for conductor.build", the agent reads that session, shows the screen, and proposes a rule whose words are on it. A question back is a first-class outcome. Nothing is stored without confirmation; nothing is armed without promotion.
Phase 4
Pro gating
Creating rules is Pro. Running them is not.

Gate rule CREATION (the smart authoring call) behind Pro. Do NOT gate running: a free user's existing rules must keep firing - a rule that silently stopped is a trust failure, and running one costs 0.4s of a cheap model.

Acceptance
A free account cannot draft or store a rule, and is told why. A free account's already-live rules still fire and still record. The boundary is enforced on the Gateway, not the client.

Deferred, on the owner's call: Director-side rules (the sign-in case, issue 2669) - needs vocabulary beyond one keystroke and steps that reach a browser and an inbox; and the "only turn red when it needs me" case, which is likely a product fix to how a session's colour is computed rather than a rule. Both wait until the harness has real screens for them.

7. The QA report - what it must prove

The point of the mission is the QA report. It must show the engine implemented AND working, on three real scenarios, each with screenshots: the screen before, the firing record, and the result after. A decline is proven the same way an act is - by the recorded firing, never by the absence of a keystroke.

Scenario C - the negative control the one that proves it is safe

StepWhat the screenshot shows
The trapA live rule whose trigger words are on the screen - but in documentation the session is reading, not in the session's own state.
The declineThe firing record: the model read it, DECLINED, and said why - "the words are in something the session is reading, not its report of its own state". Nothing typed.
Why it mattersA rule that never declines has not been shown to have a boundary. This is the proof the engine judges rather than pattern-matches - the thing a fixed word list could never do.

The report must also state what is NOT proven, plainly - the mission's own standard. Every red before its green, every claim tied to the commit it ran on, and an honest list of what was demonstrated versus what was only unit-tested.

2. What a rule can actually do

Short answer to your question: no, a rule cannot run Python. It cannot run anything. There is no interpreter in the rules engine, no shell, no eval, and no column in the database a code string could sit in. A rule does exactly one thing when it fires: it types a piece of text into one idle session. Everything else about it is deciding whether to.

What a rule cannot do - stated, not implied

A rule cannot...Because
run Python, a shell command, or any codeThere is no interpreter. A rule holds the name of a check we shipped and its argument values. There is nothing to escape from.
read or write a fileNone of the five checks touches a file. is_path_inside compares paths; it does not open them.
reach the networkNo check makes a request. The only outbound thing a rule does is a keystroke down the tunnel to the Director.
start, stop, restart or kill a sessionIt can only type into a session that exists and is idle. A dead session is unreachable.
act on a session that is workingThe only thing that wakes a rule is a session crossing from working to idle.
act at a particular timeThere is no clock. A session parked since 11pm is never looked at again. This is the gap behind your 3am case.
do more than one thingOne keystroke per firing. No sequences. This is the gap behind the sign-in case.
change how a session is displayedEvery action ends in a keystroke. This is the gap behind "it turns red and does not need me".
promote itself, edit itself, or write another rulePromotion needs evidence minted from a person's authenticated request. The evaluator has no such request and, by a structural test over the built assembly, no path to the store's promote at all.
act outside its scope or above its ceilingsChecked before any model is asked, on every pass.

The honest reading of the picture. A rule's own powers are tiny. But it types into a coding agent, and a coding agent is unbounded - that is the settled ruling, and it is why the old "allowed actions" list was never a safety boundary. So the question "what can a rule do" has a small answer, and the question that matters is "which sessions, how often, and who said yes". Those three are where the safety lives, and they are all in the dashed box above.

On the temptation to add "a little bit of Python". Every case you have named - the limit, the outage, the sign-in, the colour - is match a screen, do a named thing, maybe after a wait. None needs a language. The three that do not work today are missing a clock, a sequence, and a non-typing action - each of which is a new reviewed step shipped in a release, exactly like the five checks. Deciding whether an arbitrary script is safe is a far harder problem than any of those, and we would be taking it on to solve a problem we do not have.

The one thing your API idea changes. An agent holding a device key can call promote today. So a coding agent set loose on the API could write a rule and arm it with nobody looking. The command line deliberately ships without promote; the API still has it. The fix is agent credentials that can do everything except promote - then "Claude Code, set up a rule" always lands in dry run, and you flip it live yourself.

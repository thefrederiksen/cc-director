Session Rules: the run-time judgement, and a rethink

Written by the Architect, 4 September 2026, after Phase 1 round A missed its gate. Every number here is read off the committed harness reports, not recalled.

The owner asked for this document before any further code: lay out what we are doing, how we detect the problem, how we verify it is a problem, and how we solve it - then step back and ask whether the approach is right at all, rather than hacking another thing onto it.

I did that, and the answer is that the approach is partly wrong, and wrong in a way three rounds of work has been quietly walking away from. The detail is in section 6. This document does not ask for approval of a patch; it argues for changing the thing we have been optimising.

1. What the feature actually has to decide

A coding session goes quiet. Something has to answer one question about the last screen it printed:

The question

Is this session, right now, stuck in the exact situation the account's instruction describes - such that typing the instruction's words into it is the right thing to do?

That question has three parts which we have repeatedly failed to keep separate, and keeping them separate is most of what this document is about:

  1. Subject matter. Is this screen about the thing the instruction names - a usage allowance, a provider error?
  2. Ownership. Is the screen this session reporting itself, or displaying something about a different session, a document, a test fixture, a log?
  3. Circumstance. Is the session actually stopped and blocked by it - or merely warned about it while carrying on perfectly well?

A screen can pass 1 and 2 and fail 3. "Eighty-six percent of your weekly limit used" is about the allowance, it is genuinely this session's own state, and the session is fine. That single combination is what is left broken today.

2. The steps we take, as built

This is the current pipeline, in order. The ordering is deliberate: everything free happens before anything expensive, so the ordinary case - a session that simply finished its work - costs one screen read and never reaches a model at all.

session goes idle | [1] one pass at a time per session free a lock; without it the ceilings are walk-throughs | [2] screen unchanged? stop free | [3] rule scope: agent, repository free | [4] cooldown and daily cap free counted off the firing record | [5] QUESTION ONE - fast model "is this screen the situation the instruction names?" | answers act or decline, plus one line copied off the screen | [6] grounding: is that line really there? free deterministic | [7] QUESTION TWO - fast model "whose state does that line report?" (added in round A) | answers own or elsewhere | [8] the rule's stored checks run e.g. retry_delay_from(screen_text, now) | [9] re-read the screen before typing a session that moved on is abandoned | [10] dry run? record it and type nothing | [11] type the rule's OWN stored text nothing here composes a keystroke | every outcome above is written down as a firing, including every decline

Two properties of that pipeline are load-bearing and are not in question here, because they have been independently inspected and they hold: no generated code ever runs - an answer names a stored check and typed argument values, never a program - and a draft cannot promote itself, so a new rule types nothing until a person promotes it.

3. How we detect a problem

Not by opinion, and not by writing a unit test that agrees with us. Phase 0 built a harness, and it is the most valuable thing this mission has produced.

  • 32 real captured screens from the owner's own sessions - not synthesised, not paraphrased. 12 where the right answer is act, 20 where it is decline.
  • The negatives are adversarial: the trigger words are present on every one of them. Documentation about rate limits. A diff adding a limit-screen test constant. A report about a sub-agent that hit its spend limit. A commit hash that happens to contain 529.
  • Every case runs through the real evaluator, not a copy of it, and the answer is read off the recorded firing rather than off a return value.
  • Every case runs three times on each model, because a judgement that changes between runs is a dice roll, and the flip rate is reported as its own number.

The number the phase is judged on

Wrong answers on the negatives that would have caused typing. Not overall accuracy. A feature that is right ninety percent of the time and types into your session the other ten percent is not ninety percent good. It is unusable, because you cannot leave it switched on.

4. How we verify it is really a problem

Four disciplines, each of which exists because something got past us without it:

  • The corpus is frozen. The same 32 cases before and after. A fix that changes the test set has proven nothing.
  • The real engine, the real recorded firing. Three defects on this mission were proven only by driving a real request; every one of them had a green test suite behind it.
  • Both models, every round. The comparison is the evidence, and section 6 exists entirely because we kept it.
  • The pass condition is a presence, never an absence. An unreadable answer, a missing field, a model that never replied - all stop the act. A check that passes when something is merely absent certifies runs that never happened, and that habit has been found five times in this one feature.

6. The step back: we have been measuring the wrong thing

6.1 The thinking model is not inaccurate. It is being cut off.

Go to the per-case rows rather than the summary. Every one of the thinking model's failures on the positives reads the same way:

p06-monthly-spend-limit-with-task-list act no answer x3 60.0s TimeoutException p07-monthly-spend-limit-and-session-banner act no answer x3 60.0s TimeoutException p09-monthly-spend-limit-with-spend-dialog act no answer x3 60.0s TimeoutException p04-session-limit-hundred-percent-banner act act x2, no answer x1 60.0s TimeoutException

Not a wrong judgement. No judgement at all, cut off at exactly 60.0 seconds. Separate the answers it actually returned from the ones it was never allowed to finish:

The thinking model, counting only answers it was allowed to give

60 of 60 correct on the negatives. 18 of 19 correct on the positives. 78 of 79 overall. One genuine mistake in the entire corpus.

And it is right on precisely the cases that defeat the fast model. On the eighty-six percent banner it said: "the session is still actively running, not a session that has stopped because its usage allowance is used up." That is exactly the distinction section 1 calls circumstance, and it drew it unprompted.

6.2 Where the sixty seconds came from

It is HostedInferenceBrain.DefaultCallTimeout - a general default for model calls, shared with the voice path, where a person is sitting there waiting for a reply. It is injectable. It was never chosen for this decision.

So the whole of Phase 1 - move to the fast model, then bolt a second question on to compensate - rests on treating a borrowed latency budget as a fact about the world.

The mistake, stated plainly

We optimised for latency in the one situation where latency does not matter.

This judgement happens because a session has stopped. In the owner's headline case it stopped at three in the morning against a limit that resets at eleven at night. It is going to sit there for hours. Nobody is waiting on the answer. We spent three rounds making the answer arrive in seven seconds instead of forty-four, and paid for it in the only currency that matters here: it types into sessions it should not.

6.3 The second question asks two things at once

Its own documentation says it is deliberately not a re-judgement of the situation - it asks only whose state the line reports. But its prompt text says:

Answer "own" only when the line is this session's OWN agent reporting THIS session's OWN state right now - this session is itself stopped, blocked or waiting because of what the line says. ... Answer "elsewhere" when the line is ... a status banner about an allowance that has not actually stopped this session.

That second clause is a circumstance test smuggled into an ownership question. The evidence that it does not work is in the results: on n11 the model quoted that very clause back while declining, and on n18 - the same shape of screen - it answered "own" and let the act through.

A question that asks two things gets one answer, and you cannot tell which one it answered. That is a design fault, not a wording problem, and a third question in the same style would repeat it.

6.4 What I am not going to do

I am not adding a third question to the fast model. Each question added is another call, another chance to be wrong, and another place where two concerns get mixed. We would be tuning a model into a judgement it is measurably bad at, while a model that already makes that judgement correctly sits behind a timeout we set ourselves for an unrelated purpose.

7. What I propose instead

Keep the pipeline. Change what stages 5 and 7 are, and change the deadline.

[5] CHEAP FILTER - fast model, question unchanged | Purpose: throw away the obvious no, for almost nothing. | Evidence: in 96 answers it NEVER wrongly declined a real limit screen. | It is over-eager, which is exactly what a first-stage filter should be. | [6] grounding, unchanged - free and deterministic | [7] THE JUDGEMENT - thinking model, the FULL question, generous deadline Purpose: the actual decision, made by the thing that makes it correctly. Evidence: 78 of 79 answers correct, including every case that defeats the fast model. Cost: reached only for screens the filter flagged. Nobody is waiting.

Three things follow from that shape, and each is a saving rather than a cost:

  • The expensive call is rare. Most idle transitions never reach a model at all - the free checks at stages 1 to 4 kill them. Of those that do, the filter removes the plain no.
  • The two-question tangle disappears. One question, asked once, by one model, covering subject matter, ownership and circumstance together - which is how a person reads a screen, and demonstrably how the thinking model already reads it.
  • The safety story becomes sayable. Today it is "a fast judgement, plus a second fast judgement about the first one, plus ceilings". That is what a reader currently has to trust.

The one thing this proposal has not proven, and it is the whole risk

Unproven

Every timed-out row reads 60.0s because that is where we cut it off. We do not know how long those calls would have taken. They might finish in seventy seconds; they might never finish.

So the proposal is not "raise the timeout and we are done". It is a measurement: run the frozen 32 cases on the thinking model with a deadline generous enough that the model's own speed, not ours, decides the outcome - and find out. If a real share still never answers, this rethink fails and we say so in those words.

Two smaller things, worth doing either way and independent of the model choice:

  • p09 fails on grounding over a single space. The model cited a real line and our own citation check refused it on whitespace. That is a defect in our deterministic code, and it costs us a genuine positive.
  • The flip rate stays in the report for whichever model wins - it is the honest reliability number. Temperature is already pinned at zero; whether the hosted endpoint honours that is measured, not assumed.

8. The thing I deliberately did not change

The Gateway already knows whether a session is working or idle - ActivityState sits on the facts record and is deliberately kept out of the question. Ruling A11 says the screen is the only input to the decision, because the screen is the evidence a person can go back and check on the firing record, and a hidden signal nobody can see is not.

It is tempting to reach for it, since "is it actually stopped" is exactly the failing distinction. I am not reaching for it, for two reasons: a session showing an eighty-six percent banner between turns may well read as idle anyway, so it may not even separate these cases; and if section 7 works, it is not needed. If section 7 fails, this is the next thing to put on the table - with the owner, because it changes what the record can prove.

9. What I am asking for

One measurement round, on the frozen corpus, same gate as before - zero wrong negatives with the positives not regressing - testing the proposal in section 7 rather than a third question.

If it passes, the feature is safe to switch on and the demonstrations proceed. If it fails, we stop, and the report says the feature works under supervision and cannot be left running unattended - which is a true sentence, and a better outcome than a fourth round of tuning.

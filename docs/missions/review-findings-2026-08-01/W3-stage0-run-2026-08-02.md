## The one-sentence result

**The fold's snooze database traffic no longer scales with the number of sessions at all: 42 reads for 42
folds, exactly one per fold, against a baseline of 1,032 reads for 43 folds - twenty-four reads per fold
down to one, measured, with no remainder on either side.**

## The count, in the baseline's own decomposition

The baseline is checkable because it decomposes with no remainder. This one is given in the same form.

| | 31 July baseline | 2 August, after the fix |
|---|---|---|
| Snooze database reads | **1,032** = (30 polls + 13 sweeps) x 8 sessions x **3 reads each** | **42** = (30 polls + 12 sweeps) x **1 read per fold** |
| Folds performed (`foldDurationMs.count`) | 43 | 42 |
| **Reads per fold** | **24** | **1** |
| Reads per roster request | 34.4 | 1.4 |
| Gate acquisitions on the fold path (`snoozeLockWaitMs.count`) | 1,032 | 42 |

**The identity that decides it, written before the run: `snoozeDbReads == foldDurationMs.count`, exactly.**
It came out 42 and 42. A ratio of 3 would have meant nothing changed; a ratio near 2 would have meant only
the first of the two loops was fixed, which is the outcome this work item was specifically warned about
because it would have read like success. It is 1.

The sweep count differs from the baseline's (12 against 13) because it is a function of how many
five-second ticks fall inside a sixty-second polling window, not of anything the fix touches. Both runs
polled 30 times at the 2-second cadence. Every one of the 12 ticks folded - 30 + 12 = 42 folds - which is
what one bound Director in one tenant should produce.

## The sweep overlap guard: THIS RUN DOES NOT PROVE IT

| | 31 July baseline | 2 August |
|---|---|---|
| `sweepOverlaps` | 0 | 0 |
| `sweepSkipped` | (counter did not exist) | 0 |

**Both zeros mean the same thing, which is nothing.** The baseline recorded zero overlaps at Stage 0 with
no guard in the code at all, because one Director over eight sessions never produces a sweep slow enough
to be overtaken - the sweep took a mean of 3.9 ms against a 5,000 ms interval. A zero after the fix is
therefore an identical reading, and identical readings are not evidence. The 91-overlaps-in-98-ticks
figure the guard exists to answer came from **Stage 1**, under 800 sessions and climbing viewer load, and
that is where it has to be answered. The guard is currently proved only by its unit tests, which drive a
held-open pass and watch the skip counter move.

Recorded so it cannot be read the other way later: `sweepSkipped: 0` here is the CORRECT and expected
answer for this configuration. Nothing overlapped, so nothing was skipped.

## Latency, recorded but NOT claimed as a result

| | 31 July baseline | 2 August |
|---|---|---|
| Roster read, client side | p50 30 ms, p95 64 ms, max 138 ms | p50 13 ms, p95 27 ms, max 59 ms |
| Roster read, server side | 33 ms mean, 127 ms max | 11.5 ms mean, 56.4 ms max |
| Fold duration | (not reported at Stage 0) | 2.8 ms mean, 12.6 ms max |
| Sweep duration | (not reported at Stage 0) | 3.9 ms mean, 12.9 ms max |

Roughly three times faster on both sides. **It is not the result, and it is not a controlled comparison.**
Stage 0 is an idle floor with one viewer; it is not where a lock-contention fix pays, and thirty polls is
not a latency measurement. What makes the direction credible rather than the magnitude is that the
contamination runs the wrong way for us: this run was taken on a machine carrying 990 processes with
11.6 GB of 64 GB free, while the baseline describes "an otherwise idle fresh rig". Contention makes a new
run look WORSE, so an improvement measured through it is a floor rather than a flattering number. The
honest reading is: the direction is trustworthy, the size is not established, and Stage 1 is where the
latency question actually gets answered.

**The one-tenant deviation, stated at the figure rather than in a footnote.** This run seeded one tenant;
the baseline's Stage 0 seeded an unknown number. It changes none of the numbers above, for a mechanical
reason rather than a judgement: the display sweep folds `PushedSessionStore.KnownTenants`, which is the set
of tenants with a Director bound to the tunnel, and the roster serves only the caller's own tenant - so
with ONE Director connected, exactly one tenant is folded per sweep whether the rig seeded one tenant or
twenty. The baseline's own fold count of 43 for 30 polls plus 13 sweeps confirms it folded exactly one
tenant per tick too. One tenant is the same measurement with a smaller footprint, and it removes an
ambiguity as a bonus: with one tenant the viewer key and the Director key cannot belong to different
tenants.

## What the thing we are comparing against does NOT record

This bounds how precise any comparison can be, and it will bound the next one too unless it is written
down. It is a defect in the baseline, not in this run.

- **The tenant count of the rig the baseline's Stage 0 actually ran on is not recorded anywhere.** The
  committed `rig-provenance.json` says 20 tenants, but it was written at 15:50:05 UTC while the Stage 0
  artifact was captured at 15:46:24 UTC - three and a half minutes EARLIER - so it describes a later rig
  boot. What matters is reconstructable from the numbers (a fold count of 43 proves one tenant was
  folded), but the seeded count itself is gone.
- **The k6 version behind its client-side percentiles is not recorded** either. Not used at Stage 0 - this
  stage needs no k6 - but it will bound Stage 1's client-side comparison. This machine now has k6 2.1.0.

So the before-and-after above is honest about direction and exact about counts, and it should not be read
as though the baseline was fully characterised. It was not.

## Pre-flight and teardown

- **Before measuring**, the viewer was confirmed to see 8 sessions. A viewer seeing zero folds nothing,
  takes no read, and would have produced a beautiful zero that answered a different question.
- **After measuring**, the roster still returned 8 sessions and the Director was still connected
  (`hubConnections: 1`), so the window was not measuring a fleet that had quietly gone away.
- The rig's error stream was empty for the whole run.
- **Teardown was run:** the simulator and rig were stopped and `stop-postgres.ps1` removed the container
  with its data, verified by `docker ps -a` returning nothing for that name. No synthetic tenant survives.

## What this run does NOT show

- It says nothing about the overlap guard (see above).
- It says nothing about the ceiling or about which resource gives first now. The baseline named
  `SnoozeRegistry._gate` at roughly five concurrent viewers over 800 sessions; whether something else now
  gives first is a **Stage 1** question and is the most valuable thing still unmeasured.
- Its latency figures are an UPPER bound taken under contention, not a controlled comparison. Contention
  makes the Gateway slower, so the measured latency is the worst case and the measured IMPROVEMENT is the
  understated one - a floor is what the improvement has, a ceiling is what the latency has. (Corrected
  after the same error was found in the Stage 1 report: the two bounds run in opposite directions, and
  calling both a floor makes the weaker claim sound like the stronger one.)
- One run. The counts are arithmetic and would repeat; the latencies would not necessarily.

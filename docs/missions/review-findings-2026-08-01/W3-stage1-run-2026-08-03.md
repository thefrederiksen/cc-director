## The one-sentence result

**The five-viewer ceiling is gone.** At a hundred concurrent viewers over 800 sessions the roster now
answers in **8.3 milliseconds** against the baseline's **68 seconds**, the Gateway serves every poll
offered to it (49.8 per second against a theoretical maximum of 50), and not one request failed or timed
out - against a baseline in which 18.5 percent of requests hit the 60-second timeout.

## The read count, confirmed at scale

`snoozeDbReads` **11,813** against `foldDurationMs.count` **11,813** - **exactly one read per fold, no
remainder**, over 9,953 roster requests and 93 sweep ticks across 20 tenants. Stage 0 established this
identity on 8 sessions; it holds unchanged at 800.

Snooze gate wait, whole run: **mean 0.39 ms**, p95 2 ms, max 101 ms - against a baseline whose per-step
means ran 34 to 182 ms and whose wedge left 104 of 111 threads blocked on that monitor.

## The sweep overlap figure - AND WHAT IT DOES NOT SAY

| | 31 July | 3 August |
|---|---|---|
| `sweepTicks` | 98 | 93 |
| `sweepOverlaps` | **91** | **0** |
| Max sweeps in flight | 36 | **0** |
| `sweepSkipped` | (did not exist) | **0** |

This is the number the guard had no measured counterpart for, and it is now measured: **zero overlaps in
93 ticks, against 91 in 98.**

**But the credit belongs to the batched read, not to the guard, and the evidence for that is
`sweepSkipped: 0`.** The guard never fired - not once - because no tick ever arrived while a pass was
still running. A sweep now takes **39 ms mean** against the 5,000 ms interval, so there is nothing left to
overtake. The overlaps did not stop because they were prevented; they stopped because the thing that made
sweeps slow enough to overlap is gone.

So this run proves the OUTCOME the guard was asked for and says nothing about the guard's own behaviour.
That behaviour is proved elsewhere and deliberately: four unit tests, and a revert proof in which deleting
the `CompareExchange` block let a second pass run where the test expects none. The guard's remaining value
is as a backstop against a future sweep that becomes slow again - which is a real risk, since a sweep is
only fast while everything it folds stays fast.

## What this run does NOT show

- **It does not locate the new ceiling.** The Gateway served the entire offered load at every step, so the
  limit is somewhere above 100 viewers on 800 sessions and this profile cannot say where. The baseline's
  standard profile (100 to 5,000 viewers), which WEDGED at 500 viewers and never recovered, was not run.
- **It says nothing about the overlap guard's own behaviour** - see above. `sweepSkipped: 0` is the honest
  reading, and it means the guard was never exercised by this load.
- **Stage 2 (Director push) was not re-run.** The fold is still on the hub invocation path; moving it off
  is phase two, so Stage 2 would measure a path this work did not change.
- **One run, one machine.** The counts are arithmetic and would repeat. The latencies are a floor.

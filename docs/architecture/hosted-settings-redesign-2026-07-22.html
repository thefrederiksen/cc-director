DevThrottle · Settings Design Proposal

The Settings page: what belongs on a hosted Gateway, and what does not

Today the Cockpit Settings page paints a red error on the hosted Gateway because every setting it reads is deliberately refused there. This document decides what the page should be instead - which tabs stay, which are removed, and which settings become tenant-aware - and shows it as a mockup, so a single well-defined issue can be written from it. No code is changed here; this is the design.

Where this stands, and the model we settled on

Built already (issue #2017), and verified working on a live Gateway: the per-tenant settings store and typed resolver, the settings-page endpoints reading and writing per tenant, the snooze-default and time-zone runtime consumers, the Gateway-owned hosted signal, and the Cockpit page. On self-host every setting persists per the single local tenant today.

The model we settled on (issue #2022 - unification): self-host is the hosted Gateway with exactly one tenant (Local, SQLite behind it). One code path, one page. The machine-scoped settings leave the web page entirely: read-only diagnostics go to the About page (web, both surfaces); start-at-login moves to the installer plus a CLI command - the one home that works on every platform including a headless Linux server (a tray/menu-bar toggle is an optional convenience only where a desktop exists); network addressing is dropped (auto-resolved, shown read-only on About); and brain restart / config is removed entirely (restart is automatic; the model it set is now the per-account AI tab). So the web Settings page becomes identical on both surfaces: per-account, no "This machine" tab on either, scope pills always read "your account". Time zone stays on the page (it is a per-tenant display preference, not a machine fact). Privacy is gone.

The last step, landed as one: the deep runtime consumers (wingman models, text-to-speech, narration, car mode) are being threaded per tenant by the multi-tenant (MTR) mission; the hosted deny is retired together with that integration, so no setting is ever settable-but-not-consumed. The snooze/time-zone consumers are already threaded.

Note on the sections below. Sections 02-05 were written for an INTERIM step - "hosted drops the machine tab, self-host keeps it, pills differ per surface." That is superseded by the unified model above: after #2022 neither surface shows a machine tab on the web, and the pills are always "your account". The reasoning in those sections (why the deny existed, one-code-path, the matrix of what is per-tenant) still holds - only the "self-host keeps a machine tab" framing changes.

01

Why the page is broken on hosted

On gateway.devthrottle.com/settings the page loads its tabs, calls the Gateway for the values, and is told 404 - not found. It renders that verbatim as a red banner: "Could not load settings from the Gateway: The Gateway rejected the request (error 404)." Nothing is malfunctioning. The 404 is on purpose.

The Cockpit Settings page is, by its own header comment, "a pure client of existing Gateway endpoints." Its five tabs read one owner-settings surface - GET /gateway/settings plus a family of sibling routes for AI models, snooze, addressing, and so on. On the hosted Gateway that entire family is refused as a group (issue #1863). The refusal is a single primitive over 22 routes, and it answers 404, not 403, deliberately - the code says so:

From SettingsEndpoints.cs: "the owner settings are process-global config.json values with no tenant dimension anywhere - not in the file, the store or the routes - and the host-wide auth gate admits any enrolled device key from any account, so one subscriber would repoint or read the whole fleet's settings." 404 rather than 403 because on hosted "the owner's settings" does not exist as a concept; "not here" is the truthful answer.

So the real defect is not in the Gateway - it is that the Cockpit page was never taught that it is running against a hosted Gateway. It still shows machine-scoped tabs, still fetches denied endpoints, and paints the refusal. On a self-hosted Gateway (your own machine, single tenant) the same page works completely. The fix is a page that knows which surface it is on and, underneath it, settings that have somewhere per-tenant to live.

02

The decisions, stated plainly

Five tabs today: This machine, Notifications, AI, Car Mode, Privacy. Here is the ruling on each.

TabDecisionReasoning
This machine off the web page These configure a physical Gateway host, which a shared hosted Gateway does not have. Under the unified model they leave the web Settings page entirely: read-only diagnostics go to the About page; start-at-login goes to the installer plus a CLI command (the universal home - a headless Linux server has no tray or window, so the CLI is the only thing that works everywhere; a tray/menu-bar toggle is an optional convenience on Windows/macOS); network addressing is dropped (auto-resolved, shown read-only on About); and brain restart / config is removed outright. So there is no "This machine" tab on either surface. (Time zone is the one that STAYS on the page - it is a per-tenant display preference, not a machine fact.)
Notifications keep - tenant-aware Snooze lengths and the default become per-account on hosted. Browser notifications are already device-scoped and work everywhere.
AI keep - tenant-aware Thinking model, fast model, speech model, voice, transcription - each becomes a per-account choice. This is a headline feature of the hosted product, not an owner-only knob.
Car Mode keep - tenant-aware Model and end phrase become per-account. Hands-free fleet control is a per-user experience.
Privacy delete entirely Telemetry consent is already being removed (fleet session "remove telemetry"). Wingman training capture goes with it. The tab disappears on both surfaces.
Net result (unified model, #2022). BOTH surfaces show the same three tabs - Notifications, AI, Car Mode - all scoped to "your account." The "This machine" settings leave the web page entirely: on self-host they live in the tray app + the About page; on hosted they do not exist. Neither surface has a Privacy tab, and neither has a "This machine" tab. (The earlier "self-host keeps four tabs" line was the interim step - see the revised note at the top.)
03

The crux: global becomes tenant-aware

"Keep it, but make it tenant-aware" is not a UI tweak. It is the exact thing the deny was put there to force. The settings that stay are global today - and that is precisely why they are refused on hosted.

Look at the AI and Car Mode cards in the current page: each carries a scope pill reading "whole fleet." That pill is honest. The values are written to a single process-global config.json with no tenant column anywhere. On a shared Gateway, one subscriber changing "the thinking model" would change it for every tenant. The deny is what stops that.

You cannot simply lift the deny. The code carries its own un-deny instruction: "do NOT simply remove this deny: give each of these settings a per-tenant home (config.json has none today), migrate any global value already written, and only then restore a tenant-scoped route." The design below assumes that work is the substance of the issue.

The clean target - and the recommendation of this document - is one code path, not two:

  • Every kept setting gets a per-tenant home. On hosted (Postgres) that is a row per tenant. On self-host (SQLite) it is the single "Local" tenant's row. The reader keys by the caller's tenant in both cases.
  • The route becomes tenant-scoped and therefore safe, so the hosted deny for these families is retired - not bypassed - because the reason for it (no tenant dimension) is gone.
  • The scope pill flips from "whole fleet" to "your account" on hosted, and reads "this Gateway" on self-host, where there is genuinely one tenant.
Why one path beats a hosted fork. If self-host stayed on global config.json and only hosted got per-tenant storage, we would maintain two readers, two writers, and a deny that applies to one surface but not the other - the exact split that made the current page fragile. A single per-tenant store where self-host is "the tenant count is one" removes the deny as a concept instead of routing around it.

06

Open questions to settle first

These are the decisions that must be nailed before the issue is written, not during it.

1. Where does per-tenant settings storage live?

config.json has no tenant dimension - that is the entire reason for the deny. The kept settings need a tenant-keyed home: a table row per tenant on hosted Postgres, a single row on self-host SQLite. This is the bulk of the work. Proposed: one small per-tenant settings table, read by the caller's tenant id, defaulting to today's global values on first read.

2. One code path, or a hosted fork?

Proposed: one path. Self-host is "tenant count is one." The same reader/writer serves both, and the hosted deny for these families is retired because its precondition is gone. A fork keeps the deny alive on one surface and doubles the code that must stay in step.

3. Is time zone a machine setting or a per-account preference?

It currently lives under This machine, but it is a display preference - which local hours the dashboards render in - not a fact about the host. Proposed: treat it as per-account so it survives on hosted rather than disappearing with the machine tab. If it must stay machine-scoped, hosted simply loses it; decide explicitly.

4. Confirm full removal of the two Privacy settings.

Telemetry consent is being removed by another fleet session already. Wingman training capture must be confirmed as removed, not merely hidden - capturing wingman turns on a shared Gateway is a cross-tenant data question in its own right. If it is ever wanted back, it returns as a per-tenant setting, never a global one.

5. Provider and transcription on hosted: selector or informational?

Both have exactly one hosted option today. Proposed: render them as "included" informational rows on hosted (no false choice), and as real selectors only where more than one option exists (e.g. a self-hoster who supplies their own key). This keeps the dumb-client rule - the page shows what the Gateway says is available, and never invents a choice.

6. How does the page know which surface it is on?

The page must render the right tab set without first failing a fetch. Proposed: the Gateway already knows it is hosted (GatewayHostedMode.IsHosted); expose that on a public, always-available snapshot the page reads before choosing tabs, so tab selection is Gateway-owned (project rule 7), not guessed by the client.

07

The issue this design produces

Once the six questions above are answered, the work item writes itself. A scaffold:

Title. Make the Cockpit Settings page hosted-aware and its settings tenant-scoped

Why. The hosted Settings page shows a 404 error banner because the whole owner-settings group is refused on hosted (issue #1863). The settings we want to keep are process-global, which is exactly why they are refused. Give them a per-tenant home and the page can serve them.

In scope. Per-tenant storage for the kept settings; retire the hosted deny for those families once the route is tenant-scoped; a Gateway-owned "which tabs" signal; remove the This machine tab on hosted; delete the Privacy tab on both surfaces; flip the scope pills.

Out of scope. Telemetry removal (already in flight, separate session); any new AI provider or voice; changes to self-host machine settings beyond the storage unification.

Acceptance. On hosted, /settings shows Notifications, AI, Car Mode with no error banner, each setting saved per account and isolated from other tenants. On self-host, the page is unchanged except the Privacy tab is gone. The specification is the matrix in section 4.

Sequencing note. The per-tenant storage (question 1) is the gate. The tab-visibility and pill-copy changes are cheap and could ship first as a pure UX fix - hiding the machine and Privacy tabs on hosted removes the red error immediately - but that only hides the problem until the kept settings actually persist per tenant. Decide whether to split into a "stop the error" step and a "make them work" step, or land them together.

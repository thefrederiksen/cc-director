Where skills live

How a skill in the DevThrottle library reaches an agent on a machine, where it is written, how it is kept current, and what a skill is allowed to contain. Written 29 July 2026.

One directory, using the agents standard. Every skill is materialized exactly once, into ~/.agents/skills. Seven of the eight agent families read that path natively with no configuration at all. The one that does not is pointed at it.

The shape of a skill

A skill is a directory in the Agent Skills open standard - SKILL.md at its root, plus any files and subdirectories it needs. Every agent DevThrottle supervises reads that same directory, byte for byte.

This is the single most important fact in this document: there is no per-agent format. There is nothing to translate, no adapter to maintain, and no risk of one agent seeing a different skill from another. The only thing that ever differs between agents is which folder the directory has to appear in.

Six agents need nothing whatsoever. pi needs nothing either, though it could also be pointed by configuration. Claude Code is the only confirmed exception, and Cursor is treated the same way because its support for the shared path is undocumented rather than denied.

Why not a DevThrottle-owned directory

Inventing ~/.devthrottle/skills and pointing all eight agents at it would take seven agents that currently need zero configuration and give every one of them something that can be misconfigured. The ecosystem has already standardized the shared location. Using it means the failure surface is one link, not eight.

How the link is made

Per skill, not per directory. We never replace ~/.claude/skills itself - that folder is the owner's, and it holds skills we did not write. We link each individual skill inside it:

~/.agents/skills/repo-hygiene/          <- the one real copy
~/.claude/skills/repo-hygiene           -> junction or symlink to the above
~/.claude/skills/my-own-skill/          <- untouched, ours to never mind

Windows: a junction

A directory symlink on Windows requires administrator rights or Developer Mode. A directory junction requires neither. Verified unelevated on 29 July 2026: the symlink was refused with "Administrator privilege required for this operation", the junction succeeded and the target read through it normally. The junction is what we use.

Linux and macOS: a symlink

An ordinary unprivileged symlink. Claude Code follows directory symlinks and loads a target reached from more than one location only once, so a skill present in both the shared path and its own is not seen twice.

This is a change from the first implementation, which copied each skill into up to three per-agent directories. Copies were chosen because symlinks need elevation on Windows - true, but junctions do not, and that was the missing fact. Three copies means three things that can drift; one copy cannot disagree with itself.

How skills stay current

Two halves, deliberately separated so the network can never delay a session starting.

The network half - off the launch path

The Director fetches every enabled skill from the Gateway into its local store, when the Gateway connection goes green and then once a minute for as long as it runs. It reconciles rather than accumulates: a skill switched off or deleted on the Gateway is removed from the store. A failed fetch keeps the previous copy rather than half-writing a broken one.

The launch half - synchronous, no network

When a session starts, the store is reflected into the shared directory and the links are reconciled for the launching agent. No network call, so it cannot slow or block a launch. An unreachable Gateway means the session starts with whatever the last refresh materialized, and says so.

The practical guarantee: a session opens with skills at most about a minute old, and a skill you switch off on the Gateway is gone from disk the next time any session starts.

What a skill may contain

Any file type

The extension allow-list became a short deny-list, because an allow-list cannot be completed when the standard permits any file. We deny only what is actively dangerous to write onto a machine unasked.

Binary content

Each file declares utf8 or base64, and the size cap applies to the decoded bytes. An archive or an image is simply a binary file.

Executables

One flag per file, applied on Linux and macOS, ignored on Windows. Decided by the owner on 29 July 2026: skills may carry executables. A script without the bit does not run.

Paths inside a skill are relative and validated per segment - forward slashes only, no empty segment, no . or .., no backslash, no drive letter, no reserved Windows device name such as nul or con, and at most five segments deep. Limits are 200 files per version, 5 megabytes per file, 25 megabytes per version.

The intent is plain: anything you could have authored yourself as a skill for Claude Code, Codex, Gemini or any of the others should be publishable to the library and land intact on the far side.

Ownership - what we will never touch

  • Every directory or link we create carries a marker recording the skill id, version and content hash. Only marked entries are ever overwritten or removed.
  • A name already taken by one of the owner's own skills is left exactly as it is, and the refusal is logged - silently declining to install is the kind of thing that has to be findable later.
  • The library is an additional source of skills. A machine's own skills win a name clash.

What the agent is told

Each session's preamble carries one line per skill - name and one-line description only, which is the progressive disclosure the standard specifies. The agent loads a skill's body when it decides the skill is relevant.

The current wording, "Nothing is installed on this machine - skills are fetched, so they are always current", needs to change. The freshness half stays true and is the point. The first half stops being accurate once files are written to disk, and that sentence is told to every agent in every session. It should say that skills are materialized where this agent looks and refreshed from the Gateway.

Stated plainly: what is not yet verified

  • Claude Code traversing a Windows junction has not been observed. A junction is transparent to ordinary file operations and reading through one was verified, but the agent itself has not been watched discovering a skill that way. That is the one test worth running before this ships.
  • Cursor's shared-path support is undocumented, not denied. It is linked rather than trusted.
  • The per-agent paths were read from each agent's own documentation, not exercised end to end against all eight.

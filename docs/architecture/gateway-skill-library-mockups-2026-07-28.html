Skills live on the Gateway

Mockup screens for devthrottle_internal issue 995.

The idea in one line. The Gateway holds every skill and serves it over a REST interface. An agent arrives knowing only that the library exists. Nothing is installed on any machine, so fixing a skill is an edit on the server that is live everywhere at once - no release, no re-install, no drift between machines.

Screen three  /  What the agent side actually looks like

This is the screen that decides whether the feature works. Today an agent reads whole skill files off disk. Once the library is central, the agent must learn what exists without pulling the whole library into its context.

Injected into every session's launch briefing, next to the workflow paragraph that is already there:

[Skills] Capabilities this fleet gives you. The list below is all you get for free - fetch the full instructions only when you are about to use one: cc-devthrottle skill list every skill, one line each cc-devthrottle skill get <name> the full instructions - read before you act dev-throttle the app, the command line tools, how to drive the fleet fleet-comms talk to other sessions: list, rename, message, ask, spawn move-session relocate a live session to another Director handover write down where a session stood so a fresh one can continue Skills are held centrally and can change at any time. Fetch, never remember.

And when the agent actually reaches for one:

$ cc-devthrottle skill get move-session ok fetched from gateway · v5 · 2.1 KB · cached 15 min # move-session Relocate a live session to another slot or Director. The handover goes through the GATEWAY, never machine to machine. ...
The one number that decides this feature. The register listing above is roughly 60 words. The four skill bodies behind it are several thousand. If discovery costs the listing and only the used skill costs its body, the library is cheaper than the files it replaces. If an agent ends up pulling everything, it is worse. Every design choice should be checked against that.
The unresolved one. What happens when the Gateway is unreachable? A cached copy on the machine is the obvious answer - and it quietly reintroduces the drift this whole feature exists to remove. Whatever the caching rule is, it has to be a decision, not an accident.

Screen four  /  What comes out of the installer

The point of doing this before the release: ship with no local skill deployment at all, rather than shipping a mechanism we already intend to delete.

Today

tools/cc-director-setup/Services/SkillInstaller.cs

  • Three skill names hard-coded in an array. A fourth is a code change.
  • Each downloaded from the public repository's raw content at install time.
  • Written to %USERPROFILE%\.claude\skills\ on every machine.
  • A manifest recorded so uninstall removes exactly ours and not the user's own.
  • Fixing a typo needs a release, then every user has to update to receive it.
  • Only one agent family ever sees them. The rest get nothing.

After

the Gateway serves them

  • The installer places no skills at all. SkillInstaller is deleted.
  • The skill manifest is deleted. Uninstall has nothing of ours to remove.
  • Adding a skill is a row in a register, not a release.
  • A fix is live on every machine the moment it is published.
  • Every agent gets the same library, not just one family.
  • One paragraph in the launch briefing replaces the whole deployment.

Before any code  /  What the next session has to settle

  1. How does an agent find a skill without reading them all? Screen three proposes a short register in the briefing plus fetch-on-use. It is a proposal, not a decision, and it is the whole feature.
  2. One markdown document, or a skill with supporting files? The workflow store already has a file entity, so multi-file is available if it earns its place.
  3. Offline behaviour. Cache and drift, or fail loudly and stay honest. Pick one on purpose.
  4. Do we copy the workflow register, or extend it? Separate register sharing the storage shape is the recommendation - a skill and a way of working are different things and should not share a list.
  5. What happens to the skills that stay local? A repository can have its own skills in its own tree. Central and local have to coexist without one shadowing the other silently.

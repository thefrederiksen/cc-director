DevThrottle Session State

The authoritative machine · 14 July 2026 · read from origin/main, not from memory and not from a working tree

You asked why fixing one state rule breaks another. The answer is not that the code is sloppy. It is that the written design says the opposite of what you want, there are three competing documents and none is authoritative, and the decision "what colour is this session?" is answered independently in about fourteen places. Every fix lands in one of them. This document replaces all three, states the machine once, and lists every place that currently disagrees with it.

The law, in the owner's words (14 July 2026). This is not open for debate.

  1. If a session is working, it is BLUE. No matter what. Period, full stop. Nothing outranks Working.
  2. The Gateway owns every state, centrally. It is the ONLY thing that decides a colour.
  3. The Director decides nothing. It reports FACTS - "I am working", plus a heartbeat.
  4. When a run finishes there is no more output. We wait about ten seconds, and then it goes RED.
  5. Gray-when-controlled is a LATER, more intelligent feature. It applies ONLY to a RED controlled session. It must NEVER touch a working one.
  6. Any of those is overwritten by blue the moment it starts working again.
  7. Every device shows the same thing, always.

Explicitly superseded. This law voids the 2026-07-10 decision recorded in issue #1286 ("a controlled worker always shows the recessive Supporting colour"). That decision is the direct cause of defect 1 below. It must not be restored, and it must not be cited as precedent. If you are an agent reading this because a document or a code comment told you that a controlled session recedes while it is working - that instruction is void, and this paragraph is why.

1. Why this keeps happening

Finding 1: the specification ranks ownership above working

docs/new_architecture/state-and-color-architecture.html - which phase-2-state-color-spec.md explicitly names "source of truth" - defines colour as a first-match-wins ladder:

OrderColourFires when
1GreyOn hold, or exited
2OrangeTranscribing, or explaining
3YellowWingman reading, or preparing voice
4PurpleBackground task
5SlateControlled by another session
6GreenBrand new
7BlueWorking
8RedNeeds you

Six of the eight rules outrank Working. Slate - "somebody else owns this" - sits two rows above blue. So a controlled session that is working reports slate, and the fact that it is working is discarded. That is not a typo anybody introduced. It is the design, written down, marked as the source of truth, and faithfully implemented.

This is the mechanism of the whack-a-mole. An agent is told to fix the rail. It reads the specification. The specification says slate beats blue. It implements that. The bug returns. The next agent removes it. The one after reads the same specification and puts it back. Nothing here is anybody being careless - the document and the law disagree, and the document wins because it is written down.

Finding 1b: the same specification is also wrong in the opposite direction

The ladder is not merely out of date. It describes a system that has never existed. Twice - at lines 88 and 104 - it states:

"A sub-agent being driven by another session; it recedes so the operator is not nagged.
 Red still breaks through this."

"Red breaks through the slate "supporting" recede so a genuinely blocked sub-agent still surfaces."

The shipped code does the opposite. SessionOrdering.cs:138-139:

if (isRed && string.Equals(s.SessionRole, SessionRoles.Worker, ...))
    return "supporting";

A live-controlled Worker's red is suppressed, deliberately - the need routes to its manager instead of to you. Red does not break through. The specification's claim is a half-truth at best: red breaks through for a controlled session whose controller has died, and is suppressed for one whose controller is alive, which is the common case and the whole point of the rule.

So the document on origin/main is wrong in both directions at once. It says slate beats blue, which contradicts the law. It says red beats slate, which contradicts the code that is actually running - and did so before today's change. It matches neither the old rule nor the new one. Anyone reading it to learn how session state works comes away with a picture that has never been true of this product.

This is the strongest possible argument for why the code fix cannot ship alone. The bug is not in the code. The bug is in the paper the code is written from.

2. The machine

Three layers. Each has exactly one job. The whole design is that no layer does another layer's job.

Layer 1 - the sensor. The Director reports facts and decides nothing.

This layer already exists and is already close to right. src/CcDirector.Core/Wingman/TerminalStateDetector.cs

RuleWhereStatement
Byte means working:217-223Any single byte out of the terminal sets Working instantly and restarts the ten-second countdown. The byte is never inspected. There is no debounce on the working flip.
Ten seconds of silence means needs you:30, :296-318QuietThreshold = 10 seconds. When the stream has been silent that long, the session flips to WaitingForInput. A 250 millisecond tolerance guards a raced timer. The reason for the silence is never considered.
Exit means exitedSession.cs:2303The process ended. A non-zero code, or a death while working, is a crash.
Suppress the Director's own repaint:191-192Bytes caused by our own terminal resize are discarded, so we do not read our own repaint as the agent working.
Ignore a brand-new session's splash:200-201A session that has never had a user submission ignores bytes, so the startup banner does not paint it blue.
Screen-body rule for continuous agents:239-256For an agent whose idle terminal never goes quiet (Grok), activity means the screen body above the cursor changed, sampled at most every 500 milliseconds. A footer-only repaint is not activity.

Your ten-second rule is real, is exactly as you described it, and works. It is also published on the wire (QuietThresholdSeconds) so no client hard-codes it. The sensor is the healthiest part of this system.

Only three states are ever written. Working, WaitingForInput, Exited. The enum also declares Starting, Idle, and WaitingForPerm - nothing writes any of them. They exist only as read-side branches that can never be taken. That is very close to the machine you just described to me, which is why the sensor is not the problem.

Layer 2 - the state. The Gateway decides, once.

One function, over raw facts, producing three outputs that must always agree: a colour, a label, and a triage bucket. This is SessionOrdering, and structurally it is correct today - the Gateway runs it in one pass after the whole fleet is assembled, because deciding whether a session is a Worker needs the whole fleet, not one Director.

The proposed ladder. The only change from today is that Working moves to the top, where your law puts it.

OrderColourLabelFires when
0BlueWorkingActivityState is Working. Nothing outranks this. No exceptions.
Everything below applies only to a session that is NOT working.
1Deep redCrashedThe agent process died unexpectedly.
2Dark greyExitedThe process ended cleanly.
3GreySnoozedParked by you or by the agent, and the timer has not expired.
4OrangeTranscribingA dictated utterance is uploading or being transcribed. Do not let anyone else type into it.
5OrangeExplainingA deep dive you asked for is running.
6YellowWingman readingThe wingman is reading the finished turn. We do not yet know if it needs you.
7YellowPreparing voiceA voice-mode session is generating its spoken summary.
8PurpleBackgroundParked on its own background task, not on you.
9GreenReadyBrand new, never took a turn.
10SlateSub-agentIt needs someone, and a live controller owns it - so the need goes to its manager, not to you. This is the gray-when-controlled rule, and it applies ONLY here, at the red position.
11RedNeeds youTen seconds silent and none of the above. The only colour that drives the needs-you bucket.

What actually changed. Only the position of blue. Every other rule keeps its meaning and its relative order. That is the point: the ladder was not wrong about what orange or purple mean. It was wrong about one thing - it let six different facts erase the one fact that matters most.

Read the two halves in plain English: "If it is working, it is blue. Otherwise, here is why it is not working." Every rule below the divider is an answer to a question that only makes sense once the session has stopped.

Layer 3 - the render. Clients draw and decide nothing.

Every surface renders the Gateway's stamped colour and stamped label. No surface re-derives either. A client that cannot get a stamped answer fails loudly rather than guessing - that rule already exists in packages/client-core/src/sessions/ordering.ts and it works.

3. Who owns which fact

"Which component is authoritative?" has no single answer, and that ambiguity is what made this hard. The split is per fact, not per component.

FactOwnerWhy it can only be there
Activity: working / not workingThe Director's terminal detectorOnly the Director sees the bytes. Nothing may override it. It is pushed up as a fact, never as a colour.
Hold intent and the timerThe GatewayThe timer must survive a dead Director. That is the whole point of it.
Session role (Worker / Manager / Standalone / Architect)The Gateway"Is this session's controller still alive?" is unanswerable from one Director.
Colour, label, triage bucketThe Gateway, from the three facts aboveOne fold, one answer, every screen.

Note the consequence, because it is the thing that keeps biting: the desktop is a producer of the first fact and a consumer of the other two, at the same time. It cannot compute its own role or its own hold expiry, so it cannot compute its own colour. It must ask.

The traps - comments that lie to the next agent

These cost more than the bugs, because they are what the next agent reads before writing code. Every one of them is on origin/main right now.

  • The specification itself is the biggest trap of all - it is wrong about blue and wrong about red, and it is the first thing any agent reads. See findings 1 and 1b.
  • Five comments name SessionStatusWingman.ColorFor as the source of truth. That method was renamed in phase 2.3 and does not exist.
  • Four comments describe green, yellow, purple, orange, and slate as colours "the wingman writes onto each Session". It has not since phase 2.3. It emits only blue, red, and unknown.
  • The fold claims the Gateway "reads the Director's cooked StatusColor for NOTHING". Half true - the fold is clean, but the pipeline feeding it still gates a stamp on StatusColor == "red".
  • A dead copy of the voice rule (VoiceColorFor) still carries the bug the Gateway fixed - the one that wedged a session orange forever when text-to-speech failed - and its comment claims the Gateway "applies the same rule". It does not.
  • SessionStatusWingman and Session.cs both claim to be the "single writer" of the status colour. Three other paths write it.
  • A dead desktop fold maps Working to green and WaitingForInput to amber. Unreferenced - but it is the corpse the next agent will read and copy.
  • The role DTO documents three roles. The code produces four (it omits Architect).
  • ProactiveExplainService says the wingman defaults ON. It defaults OFF.

5. What has to change

  1. Move blue to the top of the ladder and delete the rule that lets ownership erase activity. One line. This is the fix already built and proven on a running rail; it is waiting on your word.
  2. Correct the specification, or the next agent restores the bug from the document. Retire state-and-color-architecture.html and phase-2-state-color-spec.md, fold session-state-machine-2026-07-14.html into this one, and leave exactly one document standing.
  3. Send the session role down to the desktop so it stops being the one screen that cannot suppress a worker's red. Until then, desktop and phone disagree by construction.
  4. Delete the Director's colour computation. Nothing that paints reads it. It exists only to be mistaken for the answer.
  5. Delete the six other desktop folds and the three client label folds. Every one is a future contradiction.
  6. Restore the crashed colour. A crashed session must not look like an exited one.
  7. Separate the greys, or accept that snoozed, exited, unknown, and sub-agent are the same dot to the human eye.
  8. Fix the traps. Every stale comment above, deleted or corrected in the same pass. They are not cosmetic; they are the delivery mechanism for the next regression.

6. How we prove it, and why a green test is not enough

The measurement that found this becomes the test: read the live fleet and assert that every session's desktop answer equals its phone answer equals its Cockpit answer. The earlier document ran that check and got six disagreements out of thirteen. When it reports zero, and keeps reporting zero, the job is done.

That check is the only thing that would have caught defects 5, 6, 7, and 8 - every one of which passes its own unit tests today, because each fold is internally consistent and consistent with nothing else.

7. Decisions only you can make

  1. Does blue beat orange? Your law says working is blue with no exceptions. Transcribing orange currently fires even while working. In practice you dictate at a prompt, not mid-turn, so gating orange on not-working costs nothing - but it is your call, not mine.
  2. Gray-when-controlled: build it now or later? The law says it applies only at the red position and never touches a working session. It is written into the ladder above at order 10. It is not built.
  3. Does a controlled session whose controller has died still recede? Today, a non-red one does (the fold checks only that a controller id exists, not that it is alive). A red one correctly surfaces.
  4. Snoozed, exited, crashed, sub-agent: four distinct colours, or do you accept the collision?

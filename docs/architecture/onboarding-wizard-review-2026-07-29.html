2The big one: there is no re-run mode

The wizard is constructed the same way every single time. It builds all seven canonical steps and no screen is ever told whether anything is already set up. Everything else in this section follows from that one fact.

Evidence: FirstRunWizardDialog.axaml.cs:123 - the constructor always builds FirstRunWizardModel.CanonicalOrder, with no parameter distinguishing a first run from a re-run, and no field recording one.

The clearest symptom

Re-run the wizard on a machine that is already connected to the hosted gateway. The Gateway screen shows the three choice cards with Hosted pre-selected and a button reading "Sign in and connect" - offering to enroll a machine that is already enrolled. Two screens later the Done receipt reads "Gateway connected" with the real address, because the receipt reads the saved configuration and the gateway screen does not. The same wizard, in the same run, states both.

The cause is one line: _gatewayConnected starts false (:61) and is only ever set by a successful enrollment during this run (:1302). RefreshGatewayChoiceUi (:1216) never consults GatewayConfig.Load() - but BuildDoneReceipt does, at :1419.

What a re-run should be

Your rule, applied throughout: if it already works, do not ask the user to redo it. Concretely that means four things.

  • The wizard knows which mode it is in. Pass a mode into the constructor - first run or review - derived from the completion marker the model already owns (FirstRunWizardModel.ShouldShow()). One flag, read by every step.
  • Every step opens on its current state, not on a blank slate. The gateway step opens Connected. The screenshots step opens on the folder in config. The code step already does this correctly and is the model to copy - it lists roots already registered, marked Added (:734-741).
  • The primary action changes from "set this up" to "this is set up - continue". Redoing stays available as a quiet secondary link, never the default.
  • The Done screen reports what changed this run, not what exists. On a review run a receipt of eight rows all reading Done tells the user nothing.

Your instruction, recorded

"If we're already connected, for instance if we're running this again and we're already connected to the gateway, really no reason to force people to connect again. They could reconnect, but the default would be don't connect again. If things already work, don't try to redo it."

A1Defect "Use these agents" works during the scan, and adds none

Entering the step makes the primary button visible but never disables it (:210-213), so it defaults to enabled. It is only set from the scan result at the very end (:406). Press it while the scan is running and AcceptAgentsAsync reads _agentSuggestions, which is still the empty array it was initialised to (:52), finds nothing to add, logs "nothing new to add" and advances (:529-533).

The user sees a button labelled "Use these agents", presses it, and ends up with no agents configured and no message saying so. On a fast machine the window is small; on a slow one, or where a version probe hangs near its timeout, it is wide open.

Change: disable the primary button for the duration of the scan and label it "Checking..." while it is disabled.

A2Unclear Nothing on the screen reads as activity

"Scanning this machine for coding agents..." is rendered in the wsub style - the same grey 16 point subtitle used for the static explanatory line on every other step (FirstRunWizardDialog.axaml:186-187, style at :29-37). There is no bar, no spinner, no count, no named current item. The wizard contains no progress control of any kind.

Change: an indeterminate bar, a live "Checking <agent> - 3 of 7 checked" line in accent blue, and the explicit wait request you asked for: "Please wait for this to finish. Your agents are only detected and set up correctly once the check completes."

A3Slow Probes are sequential and nothing is drawn until all of them return

ProbeVersionsAsync runs a foreach with an await per found agent, each bounded by that plugin's validation timeout (:418-435), and BuildAgentRows is only called after the whole loop returns (:388-389). So the wait is the sum of every probe, and the screen shows nothing for all of it.

Change: draw each agent's row as soon as detection finds it, with the version cell reading "Checking version..." until its probe lands. The user watches the list build, which is its own answer to "is anything happening".

T1Defect No Fix, and no state for a tool that has actually failed

The screen renders two states only, straight from a boolean: tool.IsAvailable ? "Ready" : "Installing..." (:657-661). Anything not present is called "Installing", forever. The poll runs every two seconds (:686-696) with no timeout and no escalation, so a tool that will never install keeps its "Installing..." pill while the status line above it keeps asserting "It finishes on its own; you don't have to wait." That sentence becomes false and nothing on the screen ever takes it back.

The repair already exists elsewhere. The Home screen's Fix button calls ToolUpdater.RepairPythonToolsAsync(progress) and streams live progress into its row (MainWindow.axaml.cs:1055-1061). The wizard already imports CcDirector.Setup.Engine. Adding the same action here is a small change, not new machinery.

Change: three row states rather than two - Ready, Installing, Failed. Escalate Installing to Failed when the poll sees no change for a set period. Show a "Fix this now" action whenever anything is Failed, streaming repair progress the way Home already does. And report a failed repair - the existing Home button writes the outcome only to the log file, so a repair that fails is invisible there too.

T2Wrong "Ready" means present, not working

ToolDescriptor.IsAvailable => IsBuilt || IsOnPath (ToolDescriptor.cs:92) is a pure presence check. A tool that is installed but broken - the exact case the Home screen has a whole repair path for - reads "Ready" here.

Change: use the same health check the Home screen already runs, so this screen and the Home status can never disagree about the same machine.

T-1Deferred Declining the tools is a Settings question, not an onboarding one

"I'm wondering if we should have a way to not install the tools, but I think it should be under the settings. We are going to do a different section... the tools section needs to be reviewed. So for now, we keep the onboarding wizard this way."

No opt-out is added here. Whether the tools can be declined at all becomes its own review of the tools area, and Soren is raising it with the release manager directly.

The three findings on this screen stay in scope regardless: they are about the screen telling the truth when a tool is broken, which is a different question from whether the user gets a choice about having them.

T3Unclear The trade is never stated

The current line says the background half - "It finishes on its own; you don't have to wait" - but never what waiting buys. Your wording, which I would use close to verbatim: "Wait here and all of them will be working before you finish. Continue and DevThrottle finishes the rest in the background on its own." Both halves, one sentence each, so the choice is a real one.

C-1Decided Invert it: found means added, and the action becomes Remove

"I think these should be remove instead of add. I didn't see the adds buttons, so I didn't add them. We should get them automatically added because then we can do all kinds of recommendations on them."

The screenshot is the evidence. Four folders found, Add buttons on every row, and the product's own author registered none of them. An opt-in that Soren misses is not a working opt-in. Beyond convenience: a folder we know about is one we can make recommendations on, and a folder the user never got round to adding is invisible to every downstream feature.

Changes: CodeRow at FirstRunWizardDialog.axaml.cs:781-832 (the Add button), AddCodeRootAsync at :850, and the streaming handler at :748-755 which becomes the point of registration.

One thing to be deliberate about. The wizard's stated principle is that doing nothing writes nothing (:196-200); this inverts that for one step. My recommendation is to persist the moment the row appears, because that is what the row claims - a row reading "added" that is not actually saved becomes a lie the instant the user closes the window.

C-2Decided It has to work on Mac, and today it does not work equally

Checked in CodeFolderScout.CandidateRoots() (src/CcDirector.Core/Onboarding/CodeFolderScout.cs:46-79). Both platforms probe the home directory for Projects, Code, repos, git, dev, src, plus source\repos on Windows and ~/Developer on Mac.

But the drive sweep is Windows-only (:62-77): it lists the top level of every fixed drive and takes any folder whose name looks like code. That sweep is exactly what found all four folders above - none of them live under the home directory. A Mac user keeping code outside their home directory gets nothing comparable, so auto-add would find far less on a Mac than it does here. Needs a Mac arm covering /Volumes and the common Mac locations.

The scan is capped at ten seconds (:745). When that cap fires, the cancellation handler writes "That is everywhere we checked - add anything else below." C3Defect Folders added here never reach New Session

The step writes the folder to the root directory store (:862). New Session builds its list from the repository registry and from nothing else (NewSessionDialog.axaml.cs:552-562), and is handed the registry only (MainWindow.axaml.cs:3389). So the receipt says "12 repositories - Done" and the very next screen says "No repositories yet".

The seam already exists and is already populated: RepositoryMonitor holds every repository under the registered roots, is warm-loaded from cache at startup (App.axaml.cs:247), and New Session simply never consults it. This is a read-side change, not new machinery.

C4Wrong Two comments assert the wiring that does not exist

:84 - "the roots store the board and New Session read" - and :849 - "the same roots store the board and New Session read". Both are false, and a comment that describes a wiring nobody built is how this shipped in the first place. They have to be corrected in the same change as the code, or the defect returns.

This is already the shipped design and it is exactly the "different logins" in the decision above: Chrome 136 and later refuses remote debugging on the default profile, and App-Bound Encryption refuses to carry a login into a copied profile. So each drivable browser is its own folder, signed in once by a human. That constraint is proven, not theoretical - and it is what makes signing in a human act rather than something the wizard can do for you.

Recommendations

B-1Decided One step, after Screenshots and before Gateway

It belongs beside "show, don't type" - both screens are about how an agent gets context from you - and it keeps Gateway as the last real step before Done.

Not the installer, and there is a second reason beyond the one given: the installer is finished and proven on a clean machine, and making a third-party Python tool a prerequisite would gate every DevThrottle install on it, including the majority of users who never drive a browser.

B-2Decided Recommend doing it now, with an honest way out

The screen takes a side: setting up now is easier than wiring it up afterwards, and it says so. The way out is a quiet "set up browsers later - I want to get going", with the rail named as where that happens. This is deliberately not the Code step's auto-add - nothing third-party is installed without the user choosing it - but the screen recommends rather than sitting neutral.

The consequence that shapes the step: if the recommended path installs the harness and leaves the user with nothing signed in, the recommendation was hollow - they finish the wizard no better off. So the sign-in is part of the recommended path, not a follow-up to it.

B-3Constraint One browser here, not several

Signing in is interactive and one browser at a time. Three signed-in profiles cannot be batched into a three-minute wizard, and trying would make the path we are recommending the slowest thing in onboarding. Install the harness, create one profile, sign it in, and say plainly that more are added from the Browsers group in the rail.

B-4Consent Name the tool and its source on screen

browser-harness is browser-use's software, not ours. The screen must say what it is installing and where it comes from before the user accepts. A wizard that silently puts a third party's software on someone's machine is not something we should ship, whatever the convenience.

The one real unknown - settle this before estimating the step

What does installing browser-harness actually require? It is a Python tool from browser-use. Whether that means pip, uv, or a bundled runtime decides whether this step is small or large, whether it can complete without leaving the wizard, and whether the Mac and Windows paths differ. I have not checked this yet - it is the only thing in this step that could turn out expensive, and everything else here is wiring over machinery that exists.

Related: what the screen does when the install fails. Per the no-fallback rule it says so and offers the manual install page - it never continues as though it worked.

R1Defect The step ignores the gateway that is already configured

Covered in full in section 2. In short: _gatewayConnected is a this-run-only flag (:61, set at :1302) and RefreshGatewayChoiceUi never reads GatewayConfig.Load() - while BuildDoneReceipt does (:1419).

Change: read the saved gateway when the step opens. If one is configured, open on the Connected view with the primary button reading "Continue", and put reconnecting and disconnecting behind quiet secondary links. This is a handful of lines and it is the single cheapest fix in this document.

G2Blocked The three cards cannot be operated by keyboard or screen reader

All three are bare Border elements carrying only a PointerPressed handler (FirstRunWizardDialog.axaml:369-372, 393-396, 404-407). A Border is not focusable and exposes no invoke pattern, so there is no tab stop, no space or enter, and nothing for a screen reader to announce. A keyboard-only user cannot choose a gateway at all - and choosing the hosted gateway is the commercial step of the whole product.

The wider picture: AutomationProperties is used exactly once in the entire desktop application, on the gateway status box in the main window (MainWindow.axaml.cs:685-686). Nothing in the wizard has an accessible name. This deserves its own piece of work beyond this screen.

Change: make each card a RadioButton with a card template, or a templated Button - focusable, invokable by keyboard, and announceable - and set an accessible name on each. Using PointerPressed rather than a click also means a press that drags away still selects the card.

G1Architecture This step keeps its own private ruling instead of the shared one

:58 declares a private enum GatewayChoice { Hosted, SelfHost, NotNow } and the three cards are hard-coded in markup, including which one is pre-selected and which carries the RECOMMENDED badge (FirstRunWizardDialog.axaml:369-415). Settings and the status box go through the shared state machine in CcDirector.Core/GatewayConnection/GatewayChoice.cs. So the one screen a new customer sees is the one screen that would not follow a change to the hosted rules - a region, an entitlement, an outage - while every other surface did. That is the client-is-dumb rule in CLAUDE.md, breached on the highest-value screen.

Change: collapse this step onto the shared state machine before anything else about the step is edited, so the fixes above are built on the shared ruling rather than on top of the divergence.

G3Unsourced "Part of Pro" is a hard-coded plan claim

Written directly into the markup at :387-388, with nothing behind it. If plans or trial terms change, this line does not. It is a commercial statement on the acquisition screen and it should come from the same place the rest of the product gets plan facts.

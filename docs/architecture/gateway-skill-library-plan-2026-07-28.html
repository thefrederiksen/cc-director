The central skill library

Implementation plan and screens - devthrottle_internal issue 995.

2026-07-28 · supersedes the mockup page of the same date · design settled with the owner; steps one to three BUILT, step four held behind them

Status, so this page does not go stale the moment it lands. Steps one, two and three are built and merged with this document: the Gateway holds and serves the register, the briefing carries the index through all three delivery paths, eleven command line verbs work against a real Gateway, and the Skills page is in the Cockpit. Step four - taking skill installation out of the installer - is finished on its own branch and deliberately unmerged until this lands, because an installer that deploys no skills, on machines with nothing to fetch them from, is worse than either state alone. The library only reaches real machines once a Gateway running this build is deployed; merging alone changes nothing for anyone.
One ruling changed during the build, and it is the interesting one. The plan below said the owner's switch would work like the workflow switch, which lets a PINNED read through so a seated run's conduct cannot vanish mid-run. That is wrong for skills: nothing pins a skill across time, and skill get resolves the head version and then asks for it BY NUMBER - so the exemption made the switch bypassable by the exact command every agent uses. It was found by switching a skill off on a live Gateway and watching it serve the body anyway. Off now means off on every read through the agent path, pinned or not, and the supporting files go with it. The shape of the workflow register transferred; the ruling behind it did not, and assuming it would was the mistake both times it happened in this feature.
What it is. A central repository of skills that lives on the Gateway and is served to every agent on every machine. It is an ADDITIONAL source of skills, not the only one: a machine's own personal skills and a repository's own skills stay exactly where they are, untouched and unmanaged by us. What the library adds is reach - a skill written once is available to every agent family everywhere, without a release and without anything being installed.
What it removes. The installer stops placing skills on people's machines. SkillInstaller, the skill manifest, and the uninstaller's skill removal all come out. That is why this goes in before the release: shipping the current mechanism means shipping something we already intend to delete.

Settled  /  The design decisions

These were the five open questions on the mockup page. All five are now decided.

How an agent finds a skill without reading them all
The launch briefing carries an INDEX - one line per skill, name and a single sentence - in the same block the workflow index already occupies. An agent fetches a skill's body only when it is about to use it. Nothing is written to any machine, ever. This is the whole feature, and it works for every agent family, including the ones that have no notion of a skill at all and today receive nothing.
One document, or supporting files
Files. The skills we already have cannot be represented as single documents - one is seven reference documents, another ships a Python script. SkillFileEntity copies WorkflowFileEntity exactly. Fetching a skill materialises that one skill's files into the session's own working area, at the moment of use, at the published version.
Built-ins and customisation
Exactly as workflows landed on 2026-07-24: the skills DevThrottle ships are read-only, they live once in the shared library partition, a tenant gets an on/off choice over them, and the way to customise one is to CLONE it into a skill of your own. No "edited" state on a built-in, no shipped-default-changed banner, nothing to reset.
Copy the workflow register, or extend it
Copy the shape into a separate register. A workflow is a way of working that governs a whole mission; a skill is a capability an agent reaches for mid-task. Same storage shape, own list, own page.
Offline, and skills that stay local
A fetch resolves the current version from the Gateway EVERY time; if the Gateway cannot be reached the fetch FAILS LOUDLY and says so, including the instruction not to proceed from memory - no silently stale copy, no half-working fallback. AS BUILT: a skill's body is never stored, and its supporting files are written to a cache keyed by (skill, version) and verified by content hash, because a script has to exist on disk to be run. That cache can never serve one version's files as another's, and it is never consulted instead of fetching. Local skills are untouched and win any name clash, which is how the agent harnesses already resolve it.
The one exposure worth naming now. The index rides the launch briefing, so a user running their own replacement briefing text without the skill placeholder receives no index. The workflow index already carries exactly this risk, so it is not new - but it is the one place this design can quietly deliver nothing, and the Settings preview should show it.

Built-in skills are read-only, so they can never drift from what DevThrottle ships. To change one, clone it: the content is copied into a skill of your own that you can edit freely.

Screen three  /  What the agent actually gets

The decision that makes or breaks the feature. Discovery costs the index; only a skill actually used costs its body.

In every session's launch briefing, next to the workflow index that is already there:

[Skills] Capabilities this fleet gives you - held centrally, usable by ANY agent. The lines below are all you get for free; fetch a skill in full only when you are about to use it: cc-devthrottle skill get <name> dev-throttle the app, the command line tools, how to drive the fleet fleet-comms talk to other sessions: list, rename, message, ask, spawn move-session relocate a live session to another Director, with an approval gate handover write down where a session stood so a fresh one can continue Add one, or improve one: cc-devthrottle skill pull / push / publish (drafts are private; publish is fleet-wide, instantly). Your own local skills still work and take precedence.

And when an agent reaches for one:

$ cc-devthrottle skill get move-session ok move-session v5 · 2 files · written to .devthrottle/skills/move-session/ # move-session Relocate a live session to another slot or Director. The handover goes through the GATEWAY, never machine to machine. ... Files for this skill: .devthrottle/skills/move-session/checklist.md

And when the Gateway cannot be reached - loudly, with no stale copy offered:

$ cc-devthrottle skill get move-session FAILED the Gateway at https://devthrottle-gw.azurewebsites.net could not be reached (connection timed out after 10s) Skills are held centrally and are not cached between sessions, so there is nothing local to fall back on. Fix the connection and run this again - do NOT proceed from memory of what this skill used to say.
The number this feature is judged on. The index above is about 70 words. The four bodies behind it are several thousand. Every session pays the index; only a session that uses a skill pays its body. If a change to this design would make an agent pull more than it uses, the change is wrong.

Screen four  /  What comes out of the installer

Today

tools/cc-director-setup/Services/SkillInstaller.cs

  • Three skill names hard-coded in an array. A fourth is a code change.
  • Each downloaded from the public repository's raw content at install time.
  • Written into the user's own skills folder on every machine.
  • A manifest recorded so uninstall removes exactly ours and not the user's own.
  • Fixing a typo needs a release, then every user has to update to receive it.
  • Only Claude Code ever sees them. Every other agent gets nothing.

After

the Gateway serves them; the briefing announces them

  • The installer places no skills at all. SkillInstaller is deleted.
  • The skill manifest is deleted. Uninstall has nothing of ours to remove.
  • Adding a skill is a row in a register, not a release.
  • A fix is live the moment it is published - the next fetch has it.
  • Every agent family gets the same library, not just one.
  • One paragraph in the launch briefing replaces the whole deployment.

The build  /  Storage, copied from the workflow register

Four entities, one for one with the workflow four, in their own tables. Nothing here is invented: the versioning, the read-only built-ins, the shared library partition and the per-tenant switch are all proven shapes that already run.

EntityWhat it holdsCopied from
SkillEntity Slug id, built-in flag, archived, the owner's on/off switch, latest version, published version, shipped content hash. WorkflowEntity
SkillVersionEntity An immutable content snapshot: name, one-line summary, triggers, the markdown body, content hash, who authored it, the change note. Draft / published / superseded. WorkflowVersionEntity
SkillFileEntity One supporting file on a version - validated bare file name, content, hash. Distributed content only: the Gateway and the Director never execute it. WorkflowFileEntity
SkillTenantOverrideEntity One tenant's on/off choice over a shared built-in, in the tenant's own partition. Absent means "no choice made". WorkflowTenantOverrideEntity

The build  /  Four merged steps

Each step merges to main on its own and is proved before the next one starts. The installer deletion is LAST, and only once the replacement is proved on a clean machine.

Step one - the Gateway holds the skills

The register exists, is seeded with the built-ins, and is served. No client changes at all.

  • The four entities, the store with its validation, and the Postgres migration in the SAME pull request.
  • The built-in seeder, seeded from the three skills the installer ships today, embedded in the binary.
  • The endpoints above, under /gateway/skills, inheriting the host token middleware.
  • Built-ins read-only, shared library partition, per-tenant switch - the workflow rules, verbatim.
Proved by: the store and endpoint test suites (the workflow suites are the template), plus a live call against a running Gateway showing the register and one body.
src/CcDirector.Gateway/Data/Entities/Skill*.cs · src/CcDirector.Gateway/Skills/ · src/CcDirector.Gateway/Api/SkillEndpoints.cs · src/CcDirector.Gateway.Migrations.Postgres/

Step two - agents can reach it

The index rides every briefing and the fetch verb works. This is the step that makes the feature real.

  • SkillIndexStore on the Director - the twin of WorkflowIndexStore: refreshed off the launch path, rendered once, one sanitised line per skill, capped.
  • A [SKILL_INDEX] placeholder in the briefing template, beside the workflow one, so the Settings preview shows it and a user can see exactly what their agents receive.
  • cc-devthrottle skill list / get / pull / push / publish, matching the workflow verbs.
  • skill get writes the skill's files into the session's own working area and prints the body with real paths. Held for the session, never between sessions.
  • A failed fetch fails loudly with the reason and an instruction not to proceed from memory.
Proved by: a real session on a machine with no skills installed, using a skill it could only have learned about from the briefing.
src/CcDirector.Core/Sessions/SkillIndexStore.cs · FleetPreambleTemplate · tools/cc-devthrottle/

Step three - the Skills page

The owner can see, read, clone, switch off, and author skills without touching a command line.

  • The register screen above, built as the Workflows register's twin and sharing its styling.
  • Read and clone from the row; edit and version history for skills of your own.
  • The Director's slash-command menu and the skill-to-tool map read the register from the Gateway instead of scanning the disk.
Proved by: the page driven end to end against a live Gateway, with screenshots.
apps/cockpit/src/skills/ · packages/client-core/src/skills/skillsClient.ts

Step four - the installer stops installing skills

Delete the mechanism this feature replaces.

  • SkillInstaller deleted, along with its fixed list of skill names.
  • The skill manifest deleted, and the uninstaller's skill removal with it.
  • The setup screens lose the skills step - there is nothing to choose and nothing to install.
  • The three skills already sitting on existing machines are left alone. They are the user's files now; the library does not fight them, and a local skill wins its name anyway.
Proved by: an install on a clean machine that places no skill files, followed by a session that still reaches every skill.
tools/cc-director-setup/ · src/CcDirector.Setup.Engine/SkillManifest.cs

Honest  /  What could go wrong

RiskWhat we do about it
An agent ignores the index and never fetches. The same risk the workflow index already runs, and the index line is imperative for that reason. The "recent use" column on the register is how we find out - a skill with no fetches is either unnecessary or unread, and both are worth knowing.
A user's replacement briefing text has no skill placeholder, so their agents get no index. The Settings preview shows the rendered result, and the skills page says plainly when the live briefing carries no index.
The index grows until it is a page. One line per skill, both id and summary length-capped and sanitised, a hard cap on entries with an "and N more" tail - copied from the workflow index, which already enforces exactly this.
Someone publishes a bad skill and it is live everywhere at once. That is the feature working. Publishing again fixes it just as fast, every version is kept, and the switch removes it instantly without deleting anything.
A machine is offline and an agent cannot fetch. It fails and says so. Chosen deliberately over a cached copy: a stale skill that looks current is worse than a missing one that announces itself.

Not in this  /  Out of scope

No sharing of skills between customers or any public gallery. No per-repository central skills - the library is fleet-wide, and a repository that wants its own keeps them in its own tree where they already work. No execution of skill files by the Gateway or the Director: they are content we distribute, and the agent runs them in its own session under its own permission model.

CI throughput review

Why pull-request validation is producing too many hour-long runs, what the slow tests actually do, and the safest order for cutting waste without weakening the merge gate.

Recommendation

First stop work that should never run; then shorten the work that remains. Add pull-request-only cancellation, classify documentation-only changes inside an always-created workflow, repair the desktop threading flake, and remove the four tests that deliberately wait on production-scale timeouts. Do not begin with a broad test matrix, build cache, or blanket xUnit parallelism.

  1. Cancel only superseded pull-request runs. Group by pull-request branch and use a unique run id for every non-PR event. Pushes to main, merge-group validation, and tag-triggered release runs must never be canceled by this policy.
  2. Keep the workflow alive and make the path decision explicit. A small classifier always runs; expensive jobs run only when relevant; a final CI decision job always reports whether each lane passed or was intentionally not required. Make that one job required in the main ruleset.
  3. Fix the Avalonia flake in production code. Replace the palette's process-static mutable brushes with immutable brushes. Do not quarantine 19 tests that are correctly exposing a thread-affine static initializer.
  4. Remove 19 minutes 19 seconds from the serial Gateway critical path. Move the 15:49 published-artifact proof to its own lane and replace 3:30 of real timeout waits with injectable deadlines or pure formatting checks.
  5. Then reduce harness churn and stage the suite. Run a fast gate first; start the slow Gateway lane only after the fast gate passes and only for non-draft PRs. Evaluate merge-queue batching after the gate is stable.

Current merge protection does not require CI

The active ruleset for main prohibits deletion and force-push and requires a pull request, but it requires zero approvals and no status checks. A red CI run therefore does not prevent a merge. This also means a workflow-level path filter would not block today's merges—but only because no CI result is required at all.

02 Why Gateway.Tests takes 50 minutes

The average of roughly 0.69 seconds per test is misleading. The suite is a mixed integration and artifact-verification assembly, runs every test case serially, boots real web hosts and databases repeatedly, starts child processes, publishes product binaries, reads and deletes real filesystem trees, and waits on production timeouts.

The project is deliberately serial

TestParallelization.cs contains an assembly-level CollectionBehavior(DisableTestParallelization = true). This was introduced after default xUnit parallelism starved timing-sensitive background work and produced recurring CI flakes. It is not an accidental runner default.

Re-enabling it is not a one-line optimization. The Gateway test source contains 444 process-environment mutations across 142 files, 99 explicit collection assignments, and only four collection definitions. Many tests also start web hosts, allocate ports, launch processes, and touch shared filesystem locations. The assembly-wide switch is currently the only protection for much of that shared state.

03 Target CI design

1. Pull-request cancellation that cannot touch main or releases

Use the pull-request head branch as the stable group, and run_id as the fallback for every other event. Make cancellation conditional on pull_request. This is the safe shape documented by GitHub's concurrency guide:

concurrency:
  group: ${{ github.workflow }}-${{ github.head_ref || github.run_id }}
  cancel-in-progress: ${{ github.event_name == 'pull_request' }}

For a PR, another push shares the group and cancels stale work. For push, merge_group, manual, and any future event, run_id is unique, so one run cannot cancel another. The tag-triggered release.yml is a separate workflow and remains outside this group.

Do not group on github.ref with unconditional cancellation. Every push to main shares one ref, so that common recipe cancels an earlier main validation. It also risks collisions if copied into release workflows.

2. Honest path-based omission

Do not put paths-ignore on the required workflow. GitHub documents that a workflow skipped by path filtering leaves its check pending, which blocks a merge once the check is required. See Triggering a workflow. Native path filters also inspect only the first 300 changed files in some diff cases.

Instead:

  1. Trigger the workflow for every PR as it does now.
  2. Run a lightweight changes job. Paginate the pull request's complete file list through the GitHub API. Treat only a narrow allow-list—initially docs/** and selected repository-level prose—as documentation-only. Any unknown path, workflow file, build property, solution file, source, test, script, package manifest, or classifier failure must set all build lanes to required.
  3. Condition the expensive .NET, web, and artifact jobs on those outputs. On push, merge_group, and release-like events, force every lane on regardless of paths.
  4. Add a final CI decision job with if: always(). It fails if a required lane failed, was canceled, or never reported. If a lane was not required, its step summary says exactly why: for example, "Not required: all 12 changed files are under docs/."
  5. After a successful trial, add only CI decision as a required status check in the main ruleset.

This is not a false green. The required job passes because it verified both the change classification and the lanes demanded by that classification. Conditional test jobs remain visibly skipped; the summary names the omitted work. A green test job that never tested anything is never manufactured.

3. Fix the desktop flake, do not hide it

StatusPalette initializes ten process-static SolidColorBrush instances. SolidColorBrush is thread-affine. On attempt 1 of run 3522, xUnit first touched the type from a worker thread; construction threw InvalidOperationException: Call from invalid thread. The runtime then cached the failed type initialization, so later accesses threw TypeInitializationException. Fourteen palette cases and five rail-state cases failed from one initializer event.

The direct fix is to use Avalonia.Media.Immutable.ImmutableSolidColorBrush for the static read-only palette. It implements the same solid-brush interface, preserves color and identity semantics, and has no mutable dispatcher-bound state. Validate with repeated normal xUnit runs plus the existing headless UI suite. A temporary test-thread annotation would contain the symptom, but it would leave a needlessly thread-affine static resource in production.

4. A fast gate before the slow lane

The safe staging order for code-bearing PRs is:

  1. Classify changes.
  2. Fast gate in parallel: web plus all non-Gateway .NET tests. The largest non-Gateway project measured 6:48; web measured 1:17.
  3. Slow gate only after fast success: optimized Gateway tests. On draft PRs, defer this lane; add the ready_for_review activity so it runs when the author declares the PR ready. Subsequent ready-PR pushes remain covered and superseded ones are canceled.
  4. Artifact proof in parallel with the slow gate: validate the exact publish output once rather than publishing again inside a test.
  5. Always-running decision.

This intentionally adds several minutes before the slow lane starts. That is the requested trade: later expensive work, fewer full runs after obvious fast failures, and fast feedback available while the long gate continues.

5. Merge-queue batching as the later target

The repository has no merge-queue rule today. After the required decision is stable, a merge queue is the cleanest way to batch the full suite against the latest main plus queued changes. GitHub requires workflows to handle the distinct merge_group event; see Managing a merge queue.

Recommended later policy: fast gate on PR updates, full Gateway and artifact lanes on merge_group, and the existing full non-canceling validation on every push to main. This moves the hour-long proof to the point where changes are settled and can validate multiple queued changes together. Risk is operational: a failing group delays everything behind it and needs good failure attribution. Adopt only after flakes are removed and the slow lane is near the 30-minute target.

04 Matrix, xUnit parallelism, and caching

A project matrix is not the first speedup

The premise that dotnet test cc-director.sln runs every project sequentially is not supported by the log. On run 3522, Core and Engine test hosts both started at 12:27:14Z, Gateway started at 12:27:16Z, and HostedAgent at 12:27:19Z. Project test processes already overlap on one Windows VM.

A matrix therefore buys runner isolation, not previously absent project parallelism. Splitting every project would duplicate checkout, SDK setup, restore, and possibly build; it would also create more Windows jobs while the repository is already producing too many. The useful split is only two lanes: a fast non-Gateway lane for early signal and a slow Gateway lane for scheduling. Keep the artifact proof separate because its own nested publish is independent.

Do not re-enable Gateway xUnit parallelism yet

The theoretical four-core gain is attractive, but the current suite's process-global design makes it a high-risk change. The migration cost is:

  • Inventory all 142 files that mutate process environment, not only CC_DIRECTOR_ROOT and hosted mode.
  • Move configuration behind injectable objects where possible; otherwise define exhaustive nonparallel collections by shared resource.
  • Replace fixed ports and shared filesystem roots with OS-assigned ports and per-test directories.
  • Replace timing assertions with event-driven waits or injected clocks.
  • Enable limited parallelism first, run repeated stress passes on a CI-sized machine, and compare flake rate before raising worker count.

A safer intermediate experiment is several stable, explicitly owned test shards in separate processes, because environment variables are then process-local. Even that needs an audit for fixed ports, child processes, and external filesystem paths. Start only after the directly slow tests and fixture churn are addressed; otherwise parallelism merely runs waste faster and can revive the flakes that caused serial execution.

Caching is small and not currently drop-in

On run 3522, SDK setup took 37 seconds, restore 44 seconds, build 2:36, and solution tests 50:57. A perfect NuGet cache cannot save more than the 44-second restore ceiling. The repository has no packages.lock.json; setup-dotnet's package cache requires lock files and fails when they are absent. Adding locked restore is useful supply-chain hygiene, but it is a separate change with its own review. Do not cache bin/ and obj/ across arbitrary commits; correctness risk outweighs a small fraction of the test bottleneck.

05 Approval choices

No workflow, repository rule, test, or production source has been changed as part of this review. Choose one or more implementation packages:

A
Immediate waste and reliability controls

PR-only concurrency cancellation; job-level change classifier; always-running decision check; ruleset requirement; immutable palette brushes. Lowest risk and largest immediate waste reduction.

B
Gateway slow-test surgery

Inject short deadlines into the 90s, 60s, and two 30s cases; move the 15:49 artifact proof into its own lane; refactor the three worst fixture-heavy theory classes. Target: take the Gateway critical path from 50:52 to roughly 30 minutes before any parallelism.

C
Staged PR pipeline

Fast non-Gateway gate first, slow Gateway lane only after fast success and only once a PR is ready, artifact proof alongside it, required decision at the end.

D
Later batching experiment

Enable merge queue and merge_group validation after A–C are stable. Keep every main push and every release run non-canceling.

E
Cache only

Add NuGet lock files and package caching after the test changes. Expected benefit is under one minute per Windows job; this should not displace A or B.

Owner decision requested: approve A, B, C, D, and/or E. Implementation should not begin until that choice is explicit, because A, C, and D change the CI contract for every active branch.

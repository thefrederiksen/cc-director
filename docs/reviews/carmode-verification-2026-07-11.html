Car Mode — hands-free voice control of the fleet

Proof that Car Mode works, driven live via browser-harness on SOREN_NORTH against the real fleet. 2026-07-11.

What this proves

Car Mode is the standalone, hands-free page the owner opens to run the whole fleet of agent sessions by voice — one tap in, then just talk. He ends a turn by saying “over and out”, cuts the assistant off with “stop”, and two distinct audible cues mark each turn boundary so he never has to look at the screen.

This report shows the QA Agent driving the deployed Car Mode page in a browser on this machine, against the REAL fleet: who needs you, start a session, message a session, and a destructive delete held for a spoken confirmation.

Everything below is real. Each turn was sent to the deployed POST /carmode/turn endpoint from the Car Mode page's own origin; the spoken replies and the actions are the genuine responses, and each side effect was verified against the live fleet roster.

The standalone Car Mode page (deployed)

The chrome-less, full-screen page at /m/car, gated by device key with a screen wake-lock. One clear “Start Car Mode” button, the big status orb whose color is the whole state at a glance, and the walkie-talkie instructions.

Driving the fleet by voice

Five turns, each a screenshot of the Car Mode screen showing the command and the assistant's genuine reply, with the real effect verified on the fleet. Model: Qwen2.5-72B (the shipped Car Mode default).

1. "How many sessions need me right now?" (read)

Spoken reply“There are 4 sessions that need you right now.”

The brain called list_sessions against the live fleet and answered with a real count. Asked to name them, it uses each session's human NAME and repository, never a number (mission decision 5) - for example "Local Files Manager, in the devthrottle repo".

2. "Start a new session in the cc-consult repository" (act)

Spoken reply“I started a new session in the cc-consult repository. It's called cc-consult / cea6 and is running on SOREN_NORTH.”

The brain called start_session, resolved the repository, created the session the same way the "+ New session" button does, and reported the action Started cc-consult / cea6. Verified: a real new session appeared in the fleet roster.

3. "Message the Beacon session and tell it to run the tests" (act)

Spoken reply“The message to run the tests has been sent to the Beacon session.”

The brain resolved the name to the session and called message_session. Verified end to end: the text run the tests actually landed in Beacon's terminal buffer on the real fleet (a live shell session, which received and ran the input).

4. "Delete the Sandbox Runner session" - confirmation required

Spoken reply“Deleting the Sandbox Runner session in the carmode-qa-repo repo is permanent. Please say "confirm" to proceed or "cancel" to stop.”

The destructive-action gate (mission decision 3). The brain called delete_session but the loop did not delete - it armed a per-device confirmation and asked for a spoken "confirm". The orb turns red and the screen shows the confirmation banner. Nothing was deleted at this step.

5. "Confirm" - the delete executes only now

Spoken reply“Done. I deleted Sandbox Runner.”

On the next turn a deterministic C# gate (not the model) saw the affirmative and executed the delete, reporting the action Deleted Sandbox Runner. Verified: the session was actually removed from the fleet roster. A "cancel" or any unrelated command would have disarmed it with nothing deleted.

The model decision, resolved with live evidence

The mission flagged one risk: can a fast model reliably CHOOSE tools, or does it hallucinate an action it never took? Driving the real fleet answered it, in three steps:

  1. With plain tool-choice, the fast model (Qwen2.5-72B) called the read tools and message/delete correctly but skipped start_session and hallucinated “I started a session” - no tool call, no session created.
  2. The thinking model (GLM-5.2) chose every tool reliably, but at 2–9s per turn it was too slow for a voice loop.
  3. The real fix (the Architect's hypothesis, confirmed live): force a tool call every turn (tool_choice=required) and give the model an explicit speak_answer tool to say its words. The same fast model then chose every tool correctly at ~1–2s per model call - fast AND correct.

Shipped: Qwen2.5-72B as the Car Mode default with the required-tool-choice + speak_answer guardrail, GLM-5.2 kept selectable (slower but a strong tool-caller), and the model-output boundary hardened against the malformed shapes a model occasionally emits under the guardrail (so a stray value never crashes a turn).

Car Mode's own model setting (new)

Because Car Mode runs a DIFFERENT model from the Wingman, it now has its own first-class, persisted model setting, separate from any Wingman model, on the AI Settings screen (both the phone and the cockpit). It is populated from the hosted chat models, defaults to Qwen2.5-72B, and keeps GLM-5.2 as the slower-but-reliable option. The CC_CARMODE_MODEL environment override still wins for a per-install switch.

Turn-taking and barge-in

The walkie-talkie discipline (“over and out” to send, “stop” to interrupt, no silence timer) and the two distinct audible cues are implemented and unit-tested. The definitive on-the-phone barge-in sensitivity check — can the recognizer hear “stop” over the assistant's own voice, in a moving car — is yours to confirm on the real phone; the mechanism is proven and the fallback (an on-device keyword model on the echo-cancelled microphone) is designed for if the built-in recognizer ever fails that test.

Test harness and cleanup

The drive used a minimal host bound to 127.0.0.1 only (loopback) serving the Car Mode page and the POST /carmode/turn brain; its fleet tools reached the primary Gateway for the real roster and actions. It ran no Tailscale front door, no cron engine, and no stream hub, so it could not affect the live fleet's ports or scheduled jobs.

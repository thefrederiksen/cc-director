Raising the shared high-water row does not arbitrate which writer owns that delta.

On isolated PostgreSQL instance `rev7d20`/port `55447`, I seeded token high-water 100, then arranged two real concurrent transactions from that same stale baseline: writer A proposed high-water 300 and appended growth 200; writer B proposed high-water 200 and appended growth 100. Thus the explicit upserts prevent watermark regression while the all-time/hourly statistics permanently overcount during the exact two-container overlap this port is meant to survive. The shipped proof asserts only the high-water rows and never asserts the delta totals after an interleave ([`src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathPostgresTests.cs:128`](../../src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathPostgresTests.cs#L128), [`:150`](../../src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathPostgresTests.cs#L150), [`:172`](../../src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathPostgresTests.cs#L172)).

### 2. High — two containers mint two surrogate identities for one logical display

**PROVED BY RUNNING.** Identity creation is a change-tracked insert followed by `SaveChanges` ([`src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs:237`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs#L237), [`:255`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs#L255), [`:284`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs#L284)), while the model deliberately has no uniqueness constraint over tenant/display ([`src/CcDirector.Gateway/Stats/Data/GatewayStatsDbContext.cs:31`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsDbContext.cs#L31), [`:173`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsDbContext.cs#L173)). Each process decides "new identity" from its own mirror before entering the writer.

I held writer A's transaction open after it minted repository `thefrederiksen/devthrottle`, then committed writer B's identical mint before releasing A. Both writes succeeded and PostgreSQL contained **2 `repo_identity` rows; expected 1**. Deltas and `repo_session`/`agent_session` memberships can consequently split one logical repository or agent across different ids. This contradicts the documented first-seen, case-insensitive identity invariant and is not covered by the single-writer full-batch fact ([`src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathPostgresTests.cs:320`](../../src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathPostgresTests.cs#L320)).

### 3. High — a Director counter reset is counted again after a Gateway restart

**PROVED BY RUNNING.** The fold deliberately treats a lower observed count as fresh activity ([`src/CcDirector.Gateway/Stats/GatewayInputStatsAggregator.cs:466`](../../src/CcDirector.Gateway/Stats/GatewayInputStatsAggregator.cs#L466)), and the live mirror advances down to that lower value after commit ([`:643`](../../src/CcDirector.Gateway/Stats/GatewayInputStatsAggregator.cs#L643)). The new database upsert, however, stores `max`/`GREATEST` and refuses to persist the lower post-reset baseline ([`src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs:386`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs#L386), [`:393`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs#L393)). Against the shipped SQLite path, I observed session 10 turns/300 chars, then the Director-reset values 3/40. Totals correctly became 13/340. I disposed and recreated the Gateway aggregator, then replayed the unchanged 3/40 snapshot. Totals became **16/380; expected 13/340**. The existing dropped-count test covers only one live Gateway instance ([`src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathTests.cs:116`](../../src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathTests.cs#L116)); the ordinary ten-replay fact has no reset or intervening Gateway restart. This violates the class's explicit no-double-counting-across-Gateway-restart contract ([`src/CcDirector.Gateway/Stats/GatewayInputStatsAggregator.cs:16`](../../src/CcDirector.Gateway/Stats/GatewayInputStatsAggregator.cs#L16)).

### 4. High — concurrent retention pruning archives the same old rows twice

**PROVED BY RUNNING.** Each batch carrying stat or token deltas runs a read/aggregate/insert followed by delete inside its transaction ([`src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs:209`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs#L209), [`:305`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs#L305), [`:449`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs#L449), [`:461`](../../src/CcDirector.Gateway/Stats/Data/GatewayStatsWriter.cs#L461)). There is no tenant-scoped serialization or claim on the source rows before the archive insert.

I seeded one expired token delta worth 100, then arranged two concurrent writers each adding a current delta worth 1 and pruning. Writer B completed its archive `INSERT ... SELECT` while A's delete was uncommitted, then blocked on its own delete until A committed. The final all-time sum was **202; expected 102**: each transaction preserved its current 1, and both archived the old 100. This permanently doubles aged history under concurrent PostgreSQL.

### 5. Medium — the race witness accepts an unrelated lock waiter as proof of interleaving

**PROVED BY RUNNING.** `WaitUntilAnotherSessionIsBlockedOnALock` counts every other backend in the database whose `wait_event_type` is `Lock`; it does not identify writer B's backend, transaction, table, or row ([`src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathPostgresTests.cs:420`](../../src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathPostgresTests.cs#L420), [`:428`](../../src/CcDirector.Gateway.Tests/Stats/GatewayStatsWritePathPostgresTests.cs#L428)). The comment's statement that the match is necessarily writer B is therefore an environmental assumption, not an asserted fact.

First, I broke the blocking condition by changing writer B to insert an unrelated `wingman_session` row. In the otherwise isolated database, the fact correctly failed after one minute with: `No other session ever blocked on a lock, so the two writers never actually interleaved.` Then I held an unrelated PostgreSQL advisory lock and started an unrelated backend waiting on it, kept the same non-blocking writer B, and reran the interleave. The helper returned successfully and accepted the nonexistent row race; the expected refusal exception was null. Per-instance isolation lowers the normal likelihood, but the proof itself can false-green and its claim of observed writer-to-writer blocking is stronger than what it measures.

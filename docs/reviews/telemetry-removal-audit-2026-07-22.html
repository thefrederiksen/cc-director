Executive verdict

Confirmed product policy. Self-hosted Gateways may retain local operational data required to provide features such as Your Throttle, but must never send behavioral telemetry to DevThrottle servers. DevThrottle-hosted Gateways need no telemetry consent choice and must not add separate startup, login, or usage telemetry beyond ordinary service traffic. The telemetry setting and its language are to be removed everywhere in the product.

  • The screenshot is the WPF setup/update wizard in tools/cc-director-setup. It appears on both fresh Windows installs and updates.
  • The wizard now has no sign-in token. It defaults the checkbox to ON, then writes only local config.json → telemetry.enabled; its documented account GET/PATCH cannot run on the current path.
  • The Cockpit has a second, separate fleet-wide ON-by-default setting at config.json → telemetry_consent. It is exposed in Settings → Privacy and in the Gateway settings snapshot.
  • The current sign-in implementation does not originate the login telemetry event: GatewaySignInService injects a no-op reporter. The relay and its default cloud destination nevertheless remain live and can accept events from older clients or another caller.
  • The same cross-platform Avalonia startup code runs on Windows and macOS. There is no macOS equivalent of the WPF Privacy wizard in this repository, but a macOS Director still posts the startup event to its configured Gateway.

Answer to “what does the Director send to our API servers outside the Gateway?” For telemetry, the normal production answer from this checkout is nothing directly: the active startup report targets the configured Gateway, and that Gateway keeps it local unless a startup-cloud URL is explicitly configured. The login relay is the remaining default DevThrottle-cloud telemetry path, but the current sign-in flow does not generate a login event. Both Director reporter classes can be pointed directly at an arbitrary/cloud URL through environment overrides, so removal should delete those override seams too.

Service traffic that is not telemetry

Do not confuse removal with the product services the user explicitly excluded from this review. The Director sends captured audio to its configured Gateway for transcription. Desktop text-to-speech currently posts the actual text to https://devthrottle.com/api/v1/audio/speech with model, voice, and response format; that is requested service content, not behavioral telemetry. Account, device, credit, hosted-AI, transcription, notification, and sign-in traffic owned by the Gateway is likewise service operation and needs its own privacy inventory, not deletion under this telemetry issue.

Recommended removal issue scope

P0
Stop collection and forwarding first. Remove the startup call from App.axaml.cs; delete both reporter interfaces/implementations and environment overrides; remove login/startup Gateway routes; stop constructing/starting the queue; remove Gateway bearer attachment. Ensure any persisted queue cannot flush after upgrade.
P1
Remove user-facing settings. Delete the Windows Privacy wizard step and its navigation/tests; remove the Cockpit telemetry card, old route redirect, tab alias, client module, and settings snapshot field. Keep or rename the Privacy tab only if Wingman training capture remains.
P2
Remove settings and data at rest. Delete telemetry.enabled, top-level telemetry_consent, the Director consent cache, usage-event JSONL, and Gateway queue. Add a one-time, narrowly targeted migration/cleanup so upgrades do not leave the old settings or queued events behind.
P3
Remove dormant code and contracts. Delete UsageTelemetry, GatewayTelemetryConsent, TelemetryConsentConfig, AccountTelemetryClient, DTOs, OpenAPI routes, and all behavior-specific tests. Regenerate packages/client-core/src/api/schema.ts.
P4
Clean language and documentation. Rewrite or retire the centralization plan and active product docs. Rename the two retained local service-data systems as feature history/diagnostics, narrow them to feature-required fields, and document purpose, retention, user control, and the no-forwarding boundary. Keep historical proof out of current/public product guidance.
P5
Coordinate the backend repository. This checkout references but does not implement telemetry_enabled, /api/v1/account/telemetry, and /api/v1/telemetry/login. Search the DevThrottle web/API repository for endpoint handlers, database columns, jobs, dashboards, retention, and existing rows before claiming telemetry has been fully removed.

Upgrade-data handling

  • Delete only the exact known telemetry files/keys; never rewrite unrelated configuration sections.
  • Delete or quarantine config/director/telemetry-queue.json before any old flusher can start. Leaving it behind contradicts the promise because queued login events can be delivered later.
  • Remove config/director/telemetry-consent-cache.json and config/director/devthrottle-usage-events.jsonl if present.
  • Remove telemetry.enabled and telemetry_consent through the non-lossy configuration writer.
  • Do not attempt to erase ordinary application logs wholesale; document that older logs may contain prior startup-report lines, then set a retention decision.

Separate software-agreement issue

Do not block telemetry removal on a replacement page. Track a separate issue such as “Add versioned software-agreement acceptance to setup”, with legal text/ownership, acceptance versioning, update behavior, offline behavior, and storage location defined before implementation. No GitHub issue was created during this review.

Explicitly out of scope for deletion

Normal service data is not telemetry merely because it crosses a network boundary. Prompts, audio, transcription requests, text-to-speech input, hosted-model calls, account operations, and device enrollment may continue when they are necessary to provide the feature the user invoked. They still require accurate privacy documentation and appropriate retention, but they are not controlled by—or justification for—a telemetry consent setting.

Acceptance criteria for “remove telemetry”

  1. Fresh install and update have no usage-sharing or telemetry step; the setup rail flows directly from Prerequisites to Skills (unless the future software-agreement issue changes the flow).
  2. Cockpit has no usage-telemetry card, legacy /telemetry redirect, telemetry query alias, consent API call, or consent field in the general settings response.
  3. No Director launch or sign-in code constructs or posts a telemetry event on Windows or macOS.
  4. The Gateway exposes no /telemetry/login, /telemetry/director-startup, or /gateway/telemetry-consent route and starts no telemetry retry loop.
  5. No configuration key, cache, usage-event sink, durable queue, telemetry DTO, or telemetry environment override remains.
  6. An upgrade test seeds every known old key/file, runs the migration, proves those artifacts are gone, and proves unrelated configuration/data remains byte-for-byte or semantically intact.
  7. A network-boundary test runs Director startup and sign-in against a recording HTTP handler and proves no telemetry request is attempted. Functional Gateway and hosted-service requests remain covered separately.
  8. The backend repository independently removes or decommissions the referenced account/login telemetry endpoints, storage, dashboards, and historical retention.
  9. Active documentation no longer says DevThrottle collects, shares, stores, forwards, or offers consent for usage telemetry. Third-party opt-out/reference documentation remains accurate.
  10. The two Gateway-local systems currently named telemetry retain only feature-required data, are renamed/reclassified as local service history or diagnostics, have purpose/retention/user control documented, and have tests proving a self-hosted Gateway does not forward them to DevThrottle.

Review method and limits

This was a static, read-only audit of tracked source, tests, setup tooling, Cockpit/client code, Gateway code, schemas, and documentation in D:\ReposFred\devthrottle at the commit shown above. The supplied screenshot was matched to tools/cc-director-setup/Steps/PrivacyStep.xaml. Production call sites were distinguished from test-only and dormant library code by searching constructors, interface use, route mapping, and Record/report invocations.

The external DevThrottle web/API backend is not present in this checkout, so its current storage and endpoint implementation could not be verified here. Runtime packet capture was not required to establish the source paths, but the follow-up issue should add a recording-handler or integration proof before closure.

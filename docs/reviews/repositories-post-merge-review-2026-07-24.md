# Repositories post-merge review — 2026-07-24

Scope: repository feature as shipped on `origin/main` at squash commit `c93f9b95` (PR 2095), reviewed from Git objects without modifying the working tree.

## MAJOR — Pull-request CLI capture can deadlock and leak the child process

- File/line: `src/CcDirector.Core/Git/PullRequestService.cs:185-187`
- What is wrong: `RunCliAsync` redirects both stdout and stderr, but drains stdout to EOF before it starts draining stderr. If `gh` or `az` fills the stderr pipe while stdout is still open, the child blocks waiting for stderr capacity while the parent blocks waiting for stdout EOF: neither can progress. Cancellation only cancels the awaited read; disposing `Process` does not terminate the OS process, so cancellation can also leave the CLI running after the repository tab reports a failure.
- How verified: read the shipped implementation at `origin/main`, which performs `await proc.StandardOutput.ReadToEndAsync(ct)`, then `await proc.StandardError.ReadToEndAsync(ct)`, then `WaitForExitAsync`. `PullRequestServiceTests` exercises only the pure JSON parsers and contains no process, dual-pipe, cancellation, or child-lifetime test.

## BLOCKER — A deleted remote branch is treated as proof of merge, so bulk cleanup can delete unmerged local work

- File/line: `src/CcDirector.Core/Git/GitBranchService.cs:45-52,119-138`; the same verdict at `src/CcDirector.Core/Git/WorktreeSafetyEvaluator.cs:42-50` and `WorktreeInventoryService.cs:109-132`; acting UI at `src/CcDirector.Avalonia/Controls/RepositoryDetailView.axaml.cs:271-283`
- What is wrong: `BranchSafetyEvaluator` returns safe as soon as a configured upstream ref is absent, even when the branch is not contained in `origin/main` and no merged pull request was found. Remote ref deletion does not imply merge: a PR can be closed without merge and its head deleted, or a user/automation can delete the remote ref directly. `DeleteIfSafeAsync` then deletes the local ref at its verified SHA, and the “Delete safe branches” UI applies this verdict in bulk. The identical inference labels its clean linked worktree safe to reap. If that local ref was the remaining named reference to unmerged commits, the branch action—or reaping the worktree followed by the branch action—discards the user's work from normal reach.
- How verified: `ConfiguredUpstreamProbe` uses live `git ls-remote` and reports `UpstreamGone` solely from an empty response; both evaluators make that boolean independently sufficient. The shipped integration test `Branch_WhoseConfiguredUpstreamWasDeleted_IsSafe` actually creates an unmerged commit, deletes only its remote ref, never merges it into main, and asserts the branch is safe—so the test codifies the unsafe inference rather than proving a merge.

## BLOCKER — Failed `git worktree remove` falls through to an unconditional recursive directory delete

- File/line: `src/CcDirector.Core/Git/WorktreeReaperService.cs:132-155`
- What is wrong: after a final clean-status check, `RemoveOneAsync` runs `git worktree remove` but ignores its `Success`/exit code. If the directory still exists for any reason, it calls `Directory.Delete(path, recursive: true)`. There is an unavoidable window between `git status` and `git worktree remove`; if a file is created or modified in that window, Git correctly refuses to remove the newly dirty worktree, but this code interprets the surviving directory as a locked-file cleanup case and recursively deletes it anyway. The same fallthrough applies to any other safety-related refusal from Git.
- How verified: read the acting path on `origin/main`: line 144 discards the `GitCommandResult`, lines 146-150 branch only on `Directory.Exists`, and `TryDeleteDirectory` at lines 162-171 performs the recursive physical delete. `git grep` over `src/CcDirector.Core.Tests` found no test covering `RemoveOneAsync`, a failed `git worktree remove`, or a mutation between the status check and removal.

## MAJOR — The “always-current” watcher does not observe ordinary working-tree changes and has no loss-recovery path

- File/line: `src/CcDirector.Core/Git/RepositoryWatcher.cs:12-18,80-127`; startup wiring at `src/CcDirector.Avalonia/App.axaml.cs:176-187,255-267`
- What is wrong: repository watchers observe only selected files under `.git` and explicitly ignore the worktree. Editing a tracked file, creating an untracked file, or deleting a worktree file changes no watched signal, so cleanliness, uncommitted count, dirty age, worktree verdicts, recommendations, and fleet snapshots can remain stale indefinitely. The root watcher also emits only on immediate directory create/delete/rename: `git init` in an existing folder emits nothing at the root, and a slow clone can fire its one directory event before `.git` exists, be rejected after the two-second debounce, and never be reconsidered. Finally, no `FileSystemWatcher.Error` handler or periodic reconciliation scan exists, so an internal-buffer overflow permanently loses state changes.
- How verified: `CreateGitWatcher` is rooted at `.git`; `IsSignal` accepts only `HEAD`, `packed-refs`, `refs/*`, `logs/HEAD`, and `worktrees/*`. `CreateRootWatcher` is non-recursive and watches directory names only. App startup performs one `RescanAsync`, then only synchronizes watchers after a completed scan; no periodic rescan/error recovery was found by `git grep`. The integration tests modify refs by committing or writing under `.git/refs`; none edits a worktree without a commit, initializes a repo in an existing directory, delays `.git` creation, or forces watcher overflow.

## BLOCKER — Reaping fails open when live-session discovery fails, allowing removal of an active session’s worktree

- File/line: `src/CcDirector.Avalonia/Controls/WorktreesView.axaml.cs:317-325,379-393`; destructive consumer at `src/CcDirector.Core/Git/WorktreeReaperService.cs:81-109`
- What is wrong: immediately before reaping, the view fetches the paths that must be protected. A missing provider, a provider exception, or even a null result is converted to an empty list and the operation proceeds. The production provider also converts a failed fleet lookup to this Director’s local sessions, silently omitting live sessions in other Director slots on the same machine. The set is then frozen before a potentially slow `fetch --prune` and full inventory; a session that starts in a candidate worktree after that one fetch is equally invisible. The reaper recomputes Git safety with `liveSessions: null` and removes every otherwise-safe worktree absent from the incomplete/stale protected set. Thus a roster failure or ordinary start-vs-reap race can remove the directory underneath a running agent/session. This action boundary must fail closed and coordinate/recheck at the destructive step; “best effort” is unsafe here.
- How verified: `FetchLiveSessionsAsync` catches every exception, logs “proceeding without session data,” and returns `Array.Empty`; `MainWindow.GetLiveSessionsOnThisMachineAsync` at `MainWindow.axaml.cs:4284-4317` catches a fleet failure and returns only `_sessions`; `RunReapAsync` passes the resulting set into `ReapAsync`, whose own inventory call deliberately has no live-session input. The regression test `Reap_FromASessionSittingInAWorktree_TargetsThePrimaryRepositoryPath` attaches the view to a session worktree but supplies no view `LiveSessionsProvider`; it asserts only the primary repository argument and never inspects the protected set, so the exact unsafe case remains green.

## MAJOR — Failed Git probes are published as a verified, clean repository

- File/line: `src/CcDirector.Core/Git/GitStatusProvider.cs:71-91`; `src/CcDirector.Core/Git/RepositoryStatusService.cs:78-116`
- What is wrong: `GetCountAsync` maps every nonzero/failed `git status` to the integer `0`, erasing the distinction between “clean” and “unknown.” `RepositoryStatusService` also ignores `sync.Success` and `inventory.Success`, then unconditionally emits `Success = true` and `IsClean = (uncommitted == 0)`. A permissions problem, transient process failure, corrupt repository, or unavailable Git executable therefore becomes a non-provisional “verified clean” row, eligible for fleet reporting and recommendations instead of failing closed.
- How verified: followed the shipped return values end to end: `GetCountAsync` returns `0` at line 89 for any nonzero exit; `GetStatusAsync` never checks any component’s success/error and constructs a successful row at line 114. `RepositoryStatusServiceTests` covers healthy real repositories, remote classification, and size-cache behavior; no test injects or induces status/sync/inventory failure and asserts the aggregate remains unverified.

## MAJOR — Repository history persistence can truncate and then erase the entire history

- File/line: `src/CcDirector.Gateway/Streaming/RepoHistoryStore.cs:187-223`
- What is wrong: every snapshot rewrites the only history file in place with `File.WriteAllLines`. A process crash, disk-full condition, or interrupted write after truncation leaves a partial/corrupt JSONL file and no previous copy. On the next process, `Load` installs an empty/partial in-memory dictionary before parsing, catches the first malformed line, and treats that partial dictionary as successfully loaded; the next accepted snapshot rewrites the file from it, permanently erasing every row that was not parsed before the damage.
- How verified: inspected the shipped load/save order and the absence of a temp-file + flush + atomic replace/backup protocol. `RepoHistoryStoreTests` proves ordinary round-trip and legacy-row filtering only; it has no interrupted-write, corrupt-middle-line, disk-full, recovery, or preservation test.

## MINOR — Full repository snapshots never remove absent rows from today’s history

- File/line: `src/CcDirector.Gateway/Streaming/RepoHistoryStore.cs:69-112`
- What is wrong: `ObserveSnapshot` receives a Director’s full current snapshot but only upserts rows present in that snapshot. It does not delete same-tenant/same-day/same-Director rows that disappeared. A repository removed, moved, or renamed after an earlier push therefore remains in today’s dirty callouts and is double-counted in the day/week totals alongside its replacement.
- How verified: the identity includes tenant/date/Director/path, yet the observation loop has no reconciliation pass for keys owned by that Director and day. The tests cover last-write-wins for a row that remains present, but never push `[repo]` followed by `[]`, or old path followed by new path, and assert the old row disappears.

## MAJOR — A superseded stream can reclaim repository ownership by sending `Hello` again

- File/line: `src/CcDirector.Gateway/Streaming/DirectorHub.cs:121-156`; `src/CcDirector.Gateway/Streaming/PushedRepositoryStore.cs:44-58`; repeated sender at `src/CcDirector.ControlApi/GatewayStreamClient.cs:338-370`
- What is wrong: the hub permits `Hello` repeatedly when the connection is already bound to the same Director ID. `RegisterConnection` treats any connection different from the current one as a new owner and resets its sequence baseline. Consequently, after connection B supersedes connection A, A can issue its periodic reseed `Hello`, become current again, and overwrite B; B’s next periodic `Hello` reverses ownership. Two overlapping Director processes/reconnect generations can therefore alternate the supposedly authoritative repository snapshot and session roster indefinitely.
- How verified: traced the production periodic `ReseedAsync`, which always invokes `Hello` before snapshots. The store test suite covers (a) an old push without a new `Hello` being rejected and (b) repeated `Hello` from the currently active connection retaining its baseline, but never the critical sequence `register A → register B → register A again → A push`.

## MAJOR — Repository history is unbounded and rewrites the global all-tenant file on every periodic push

- File/line: `src/CcDirector.ControlApi/GatewayStreamClient.cs:142-149,338-375`; `src/CcDirector.Gateway/Streaming/DirectorHub.cs:75-83`; `src/CcDirector.Gateway/Streaming/RepoHistoryStore.cs:69-112,210-223`
- What is wrong: each Director periodically re-pushes its full repository snapshot; every accepted push synchronously enters the one global history lock and rewrites every historical row for every tenant, even when today’s values are unchanged. Rows are never aged out although the only reader caps requests at 26 weeks. The file and in-memory dictionary therefore grow forever, and write cost grows with all past tenants/directors/repos. On a hosted Gateway this also creates a noisy-neighbor path: one tenant’s large/frequent snapshots hold the global lock and force whole-file serialization that blocks other tenants’ ingest/report reads.
- How verified: followed the periodic `ReseedAsync → PushRepoSnapshot → ObserveSnapshot → Save` path. `Save` uses `_rows!.Values` without retention or change detection. Tests use a handful of rows and explicit calls; none exercises production cadence, multi-tenant contention, retention, file-growth bounds, or verifies that unchanged same-day observations avoid disk writes.

## MAJOR — Superseding a monitor scan neither cancels its first Git probes nor terminates canceled Git children

- File/line: `src/CcDirector.Core/Git/RepositoryStatusService.cs:78-81`; `src/CcDirector.Core/Git/GitSyncStatusProvider.cs:17-54,109-128`; `src/CcDirector.Core/Git/GitStatusProvider.cs:37-59,121-153`; `src/CcDirector.Core/Git/GitCommandRunner.cs:39-75`
- What is wrong: the monitor passes a cancellation token into its compute, but repository status invokes sync-status and status-count APIs that expose no token. A superseded scan therefore keeps running those processes while the replacement scan waits on the same per-repository semaphore. `GitSyncStatusProvider` redirects stderr but never drains it, and `GitStatusProvider` drains stdout to EOF before stderr, so a filled error pipe is another non-cancellable deadlock. Later worktree probes do receive the token, but `GitCommandRunner` only cancels `WaitForExitAsync`; it never kills the child, and disposing `Process` does not terminate it. Repeated refreshes can leave Git/`ls-remote` processes behind, and one hung credential/network/process pipe can prevent the “new” scan from progressing while watcher recomputes remain deferred.
- How verified: followed the default (non-test-injected) `RepositoryMonitor.DefaultCompute` call chain. The cancellation-heavy monitor tests inject cooperative compute delegates; they do not run the real sync/status providers, assert process termination, or prove a replacement scan can pass a hung predecessor.

## MINOR — The worktree confirmation is not bound to the worktrees it names

- File/line: `src/CcDirector.Avalonia/Controls/WorktreesView.axaml.cs:267-325`; `src/CcDirector.Core/Git/WorktreeReaperService.cs:81-109`
- What is wrong: the confirmation builds `toRemove` and displays those paths, but stores none of them. Confirming calls a reaper that recomputes and removes every worktree currently classified safe. If another worktree becomes safe between opening the confirmation and executing it, that new path is removed without ever appearing in the owner-approved list.
- How verified: the only values passed across the confirmation boundary are the repository path and live-session protected paths; there is no approved-target set to intersect with the freshly verified safe set. Existing reaper-view tests bypass the confirmation and assert the repository argument, not target binding across a state change.

FAIL

1. BLOCKER - A failed reservation write is still treated as a successful lease and does not stop the session process from starting (`src/CcDirector.Core/Git/WorktreeReservationStore.cs:109-132`, `src/CcDirector.Core/Sessions/SessionManager.cs:656-669`).

   Exact failing scenario: the reservation directory is readable/listable and its existing `.reap.lock` can be opened, but creating the session's JSON/temp file is denied by an ACL, antivirus filter, or transient I/O failure. `Reserve` catches the exception and returns no failure signal. `SessionManager` therefore calls `backend.Start` anyway, and its post-start `RaiseSessionCreated` retry is equally best-effort. Before the new session reaches the Gateway roster, another Director acquires `.reap.lock`, reads no reservation, and removes the old, clean worktree under the now-running session. The lock closes only the successful-write interleaving; it does not make reservation acquisition mandatory.

2. BLOCKER - Per-record reservation read/parse failures still fail open (`src/CcDirector.Core/Git/WorktreeReservationStore.cs:158-177`, `src/CcDirector.Core/Git/WorktreeReaperService.cs:273-296`).

   Exact failing scenario: a live session has a valid reservation for W, but antivirus or another process temporarily holds that JSON file without read sharing (or the file is corrupt). Directory enumeration succeeds, then `File.ReadAllText`/deserialization fails. Lines 171-177 convert the failure to `r = null` and silently contribute no protected path; they do not throw as the fail-closed contract requires. With a lagging roster and old activity timestamp, the reaper's inside-lock read is therefore an authoritative empty set and it removes W under the live session.

3. BLOCKER - Owner death is equated with session death even though session child processes can outlive the Director (`src/CcDirector.Core/Git/WorktreeReservationStore.cs:180-208`, `src/CcDirector.Core/ConPty/ProcessHost.cs:99-109`, `src/CcDirector.Core/Sessions/SessionManager.cs:853-863`).

   Exact failing scenario: Director B launches an agent in W and is then force-terminated. The child (or a detached child it spawned) survives; the launch code assigns no kill-on-close job object, and the startup orphan scan explicitly acknowledges agent processes left by a previous run. After B's stale Gateway registration ages out, Director A probes B's PID as `Gone`; lines 185-208 delete B's reservation on the false premise that all its sessions are gone too. A then removes W while the surviving agent process is still using it. Liveness must be tied to the protected process/tree, or abrupt owner death must provably terminate that tree before pruning.

BLOCKER - A delta from a superseding connection can make the prior connection's incomplete roster fresh and also cause the new full snapshot to be rejected (`src/CcDirector.Gateway/Streaming/PushedSessionStore.cs:126-135`, `src/CcDirector.Gateway/Streaming/PushedSessionStore.cs:207-224`, `src/CcDirector.ControlApi/GatewayStreamClient.cs:338-355`, `src/CcDirector.ControlApi/GatewayStreamClient.cs:393-400`).

   Exact failing interleave: connection A's cached roster omits live session T. Connection B's `ReseedAsync` allocates sequence N, sends `Hello`, and the Gateway resets `ReceivedAtUtc`. Before B reaches `PushSnapshot`, a session event calls `NotifyDelta`, allocates N+1, and sends it first. `ApplyDelta` retains A's old dictionary, sets `LastSequence = N+1`, and marks that partial set fresh. B's authoritative snapshot at N is then rejected as stale. `/sessions` serves the incomplete set as fresh/Online until a later periodic reseed; a reaper can consequently omit T (immediately destructive for a mixed-version/unreserved session, or in combination with findings 1-2). Resetting the timestamp is insufficient unless only a full snapshot can establish freshness for the new connection epoch.

5. BLOCKER - Canonicalization still fails open into incomparable path identities (`src/CcDirector.Core/Git/WorktreeReaperService.cs:530-560`, `src/CcDirector.Core/Git/WorktreeReservationStore.cs:118-126`).

   Exact failing scenario: a session launches through junction alias `D:\aliases\W` while `CreateFileW` transiently cannot open that path (an ACL/SMB/filter-driver error that clears before process start). `NormalizePath` silently stores the lexical alias because `TryResolveFinalPath` returned null. The reaper later opens Git's `D:\repos\W` path successfully and canonicalizes it to the real target. During the pre-roster launch window the stored alias does not cover the real path, so the reaper removes W. A safety identity cannot silently mix canonical and lexical forms; inability to canonicalize either side must abort the destructive comparison.

6. BLOCKER - A persisted leftover still identifies an object only by pathname, so pathname reuse for unrelated data is recursively deleted (`src/CcDirector.Core/Git/WorktreeLeftoverStore.cs:7-10`, `src/CcDirector.Core/Git/WorktreeReaperService.cs:417-470`).

   Exact failing scenario: P is recorded after repo A deregisters an old worktree. The owner manually deletes the remaining build output, then creates a new ordinary directory containing valuable files at P (or creates a worktree for repo B at P) before the next reap of A. The stale record remains. Repo A's `git worktree list` cannot identify the replacement, no reservation need exist, and lines 464-470 recursively delete it. Repository scoping and a same-repository registration check do not establish that the directory currently at P is the orphan originally recorded; a stable filesystem identity/marker is required.

7. BLOCKER - The same-repository registration guard is neither fail-closed nor current at deletion time (`src/CcDirector.Core/Git/WorktreeReaperService.cs:426-470`).

   Exact failing scenarios: (a) the initial inventory sees a newly re-registered, dirty worktree at leftover path P, but the retry's second `git worktree list` transiently fails; lines 429-432 leave `registered` empty and continue, so P and its uncommitted work are deleted. (b) the retry list succeeds before P is registered, then another process completes `git worktree add P` while the reaper waits for the reservation lock; Git registration does not participate in that lock, the cached set remains stale, and lines 456-470 delete the new registered worktree. A failed list must abort, and the registration proof needs exclusion or a final atomic/fail-closed recheck at the destructive step.

8. MAJOR - Leftover persistence remains best-effort and process-local, so the only retry record can still be lost (`src/CcDirector.Core/Git/WorktreeLeftoverStore.cs:27-35`, `src/CcDirector.Core/Git/WorktreeLeftoverStore.cs:55-97`, `src/CcDirector.Core/Git/WorktreeReaperService.cs:389-404`).

   Exact failing scenario: Directors A and B concurrently record leftovers P and Q. Each store has its own `_gate`; both read the same old JSON set, and the last fixed-temp-file replace wins (or one write fails and is swallowed). Both reapers proceed to physical deletion without any success acknowledgement from `Add`. If P remains locked, Git has already deregistered it, inventory cannot rediscover it, and its lost record is never retried. Moving `Add` before deletion does not close round 5's lost-record failure unless persistence is cross-process serialized and failure stops or is surfaced by the destructive workflow.

9. MAJOR - Cancellation after the last non-cancellable removal still discards the completed outcome (`src/CcDirector.Core/Git/WorktreeReaperService.cs:296-321`, `src/CcDirector.Core/Git/WorktreeReaperService.cs:336-340`).

   Exact failing interleave: the caller cancels while the final `git worktree remove` is running. That command correctly ignores cancellation and completes, and line 296 appends the removed outcome. The loop then exits and line 312 runs the final prune with the already-cancelled caller token. `GitCommandRunner` throws `OperationCanceledException`; the outer catch at lines 318-321 returns `ReapResult.Failure`, whose outcomes are empty. The worktree was destructively removed but the caller is told about none of it. The final cleanup must be non-cancellable (or its cancellation must return `BuildResult`) just like the per-worktree destructive unit.

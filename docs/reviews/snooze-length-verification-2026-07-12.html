Snooze Length - Mission Verification Report

DevThrottle · verified 2026-07-12 · all three phases merged to origin/main

Snooze used to be open-ended: you tapped Snooze, the session went grey, and it stayed that way until something new happened to it. When a session died or went quiet, nothing new ever happened, so the snooze never lifted and the session fell off the radar forever. This mission turned snooze into a time-bounded hold with a guaranteed return - a dead-man's switch. The worst case is now: every snoozed session comes back. You can no longer lose a session by snoozing it.

How it works

  • The timer lives on the Gateway, not the Director. That is the whole point: the timer must fire even when the owning Director is offline or the session is dead. A persisted registry (sessionId -> SnoozeUntilUtc) is re-armed from disk on every Gateway restart, so a restart mid-snooze never loses the hold.
  • Expiry re-uses the one shared fold. When a snooze elapses, the Gateway's /sessions aggregation overrides OnHold to false on the aggregated session, so SessionOrdering.Classify puts it straight back into "needs you" with no new classification logic. The overlay is pure and continuous, so the roster never flickers back to "Snoozed" between expiry and the Director confirming the clear.
  • The phone push reaches you for free. The existing needs-you notifier already watches that bucket; an expired snooze raises the count and buzzes the phone - announced exactly once with distinct copy, then it folds into the silent dot and never re-buzzes (even a lingering dead-Director snooze).
  • Nothing is written into the session's conversation. The "Snooze ended" marker lives only in roster and notification metadata.
  • All surfaces go through the one Gateway hold command, including the desktop - which in Phase 3 was converted from an in-process Session.OnHold set (which gave no timer) to a Gateway round-trip behind the IGatewayHold.RecordHoldAsync seam.

The centerpiece: a snoozed session cannot be lost

The mission exists because an enrichment session once went wrong, nothing surfaced it, and the owner had no way to know it needed him. The dead-Director end-to-end test reproduces exactly that and proves the fix:

  • a session is snoozed and held;
  • its whole Director is then killed;
  • the Gateway can no longer reach it - yet the last-known cached roster still carries the session, and the expiry overlay returns it to "needs you" on its own, marked "Snooze ended".

Test: SnoozeEndToEndTests.A_dead_director_snooze_still_returns_to_needs_you_from_the_cached_roster - boots a real Gateway on an ephemeral loopback port (no Tailscale front door), drives the real POST /sessions/{sid}/hold, kills the fake Director, and asserts the session comes back as needsYou with SnoozeExpired = true.

Cross-mission note

The desktop-to-Gateway hold rides a plain HTTP call today, deliberately behind the single IGatewayHold.RecordHoldAsync seam. The Gateway Cleanup mission is migrating all Director-to-Gateway traffic onto the tunnel; its Architect ruled Option A now and logged snooze-hold as the first named customer for the tunnel's future Director-initiated unary upstream verb. When that lands, the swap from HTTP to tunnel is a one-line change of the seam's implementation, nothing else.

All four snooze surfaces

Because the marker, colour, label and triage bucket are all computed by the ONE Gateway fold and rendered verbatim by every client, the four Snooze surfaces are consistent by construction, not by four separate implementations:

Desktop rail (ToggleSessionHold)Director -> Gateway via IGatewayHold (Phase 3)yes

A Director with no verified Gateway connection cannot snooze: the button reports "you need to be connected to a Gateway to use snooze" and sets no hold - a stated limitation, never a silent local timer.

# MTR-14A - Device-registry persistence: additive schema + one-time importer

## The problem (confirmed by audit-d)

`DeviceRegistry.Save()` rewrites the ONE shared `devices.json` file in place on every hosted enrollment. On
the hosted Gateway that single file holds EVERY tenant's device-key binding on shared infrastructure, and the
rewrite is:

- **non-atomic** - a full-file serialize-and-overwrite, so a crash or a concurrent writer can leave it
  truncated or interleaved;
- **guarded only by a process-local lock** - `_saveLock` is in-process, so two Gateway replicas over the same
  file (or the same store path on shared storage) split-brain;
- **unbounded** - the whole registry is re-serialized on each enrollment, so it grows with every tenant and
  every enrollment is O(all devices).

The blast radius is all tenants: one tenant's enrollment can corrupt or exhaust EVERY tenant's authentication
state. The fix is to make each enrollment an insert/update of its OWN row inside a database transaction, which
removes the shared-file blast radius. That runtime cutover is **MTR-14B**; this increment (**MTR-14A**) lays
the durable schema and migrates the existing file into it, additively, changing no runtime read or write.

## Scope of MTR-14A (this pull request)

Purely additive. NO `DeviceRegistry` runtime cutover, NO GatewayHost change.

1. **New EF entity `DeviceCredentialEntity`** (`device_credentials` table) holding exactly what issue #1899
   stores per device: the SHA-256 key hash (never the key), the non-secret masked identity
   (`KeyPrefix` / `KeyLast4`), machine name, issued-at, status, the mirror attributes
   (platform / device type / cloud id), and the hosted account binding (`AccountSubject` / `TenantId`).
2. **`revoked_at_utc` + `revoked_reason` columns now**, ahead of the MTR-15 tombstone work, so MTR-15 needs no
   second migration.
3. **Both migrations** - SQLite (`src/CcDirector.Gateway/Data/Migrations`) and PostgreSQL
   (`src/CcDirector.Gateway.Migrations.Postgres/Migrations`) - generated by `dotnet ef`, snapshots in sync.
4. **New EF entity `DeviceImportMarkerEntity`** (`device_import_markers` table) - the idempotency record for the
   import.
5. **`DeviceRegistryImporter`** - a durable, transactional, MARKED, one-time importer that migrates the existing
   `devices.json` into `device_credentials`. The device rows and the marker commit in a SINGLE transaction, so a
   marker exists only when the import completed in full; a second run finds the marker and does nothing (a
   restart / redeploy / retry can neither duplicate a row nor resurrect a device revoked after the import). It
   is NOT wired into Gateway startup - MTR-14B decides when it runs, after the runtime can read from the table.

### Why the table is GLOBAL (not tenant-scoped)

`device_credentials` is an AUTH-RESOLUTION lookup, exactly like the `tenants` account-to-tenant mapping: a
presented key is resolved to its device by its key hash BEFORE any tenant is known, and the tenant is then read
OFF the matched record. Scoping the table to a tenant would make that resolution circular. Each row carries its
own tenant binding as a column, so a key can only ever resolve to its OWN bound tenant - never cross-tenant. It
is therefore deliberately NOT derived from `TenantScopedEntity`, and is added to the
`TenantScopeGuardTests` global-table allowlist with that reason (a conscious act, per the guard's rule).

The lookup index is on `DeviceKeyHash` (mirroring the in-memory `_byKeyHash` O(1) index of #1899). The
Postgres natural-key columns (`DeviceId` primary key, `DeviceKeyHash` lookup, `SourcePath` marker key) carry
the explicit byte-ordinal `"C"` collation so equality/ordering match SQLite's default BINARY collation exactly
on both providers.

## Deploy note - THIS IS AN EF MIGRATION THAT MUST DEPLOY ALONE

MTR-14A adds two tables and both provider migrations. Per the fleet law that EF migrations are serialized
fleet-wide, this pull request must be deployed on its OWN, not batched with another migration-bearing change.

## Proof

Verify-first is N/A (this is additive schema, not a behavior change). Instead:

- **Real-Postgres migration-applies-clean** - `DeviceCredentialImportPostgresTests` +
  `PostgresProviderProofTests`, run against an actual PostgreSQL 16 container
  (`CC_GATEWAY_TEST_PG_CONNECTION` set): the migration applies clean from nothing, both device tables land under
  the `gateway` schema (none under `public`), and exactly the three device natural-key columns carry the
  explicit `"C"` collation. PASSED.
- **Import-preserves-rows** - `DeviceCredentialImportTests` (SQLite) and
  `DeviceCredentialImportPostgresTests` (real Postgres, through the runtime `GatewayDatabase` wiring): every
  device row and every column - including the null variations and the tenant binding - round-trips losslessly.
  PASSED.
- **Idempotent re-import** - a second `Import()` finds the marker and writes nothing, even when the source file
  has grown in between. Proven on both SQLite and Postgres. PASSED.
- **Legacy plaintext migration** - a pre-#1878 plaintext-only record is hashed with the identical transform on
  import (lossless) and the plaintext never reaches the table. PASSED.
- Also fixed a pre-existing latent drift in the gated `PostgresProviderProofTests` collation assertion (its
  expected set predated the `tenants` collation and never listed `tenants.Id` / `tenants.AccountSubject`); the
  set is now complete and passes on real Postgres.

Full Gateway test suite: 0 failures on the default SQLite run; the gated Postgres proofs pass against a
throwaway container.

## What is deliberately NOT here (MTR-14B / MTR-15)

- No change to `DeviceRegistry`'s runtime reads or writes (still the JSON file) - MTR-14B cutover.
- The importer is not wired into Gateway startup - MTR-14B.
- The tombstone lifecycle that populates `revoked_at_utc` / `revoked_reason` - MTR-15 (columns exist now).

1. **[P0] `tools/cc-director-setup-engine/LauncherStopper.cs:190-203` — the macOS process parser cannot recognize the real installed launcher path, so the original orphan remains unfixable.** `ps -axo pid=,args=` does not quote an executable path containing spaces, but the code takes `args.Split(' ', 2)[0]` as the executable. For the production path `/Users/<user>/Library/Application Support/cc-director/launcher/cc-launcher --managed`, it records `/Users/<user>/Library/Application`, which fails the install-directory filter at lines 86-89. With the token missing (the exact wiped-Mac reproduction), `ours.Count` is zero and `Stop()` returns failure without stopping the process. If `/bin/ps` is unavailable or times out, the catch produces the same empty list. Worse, `Uninstaller.Apply` only adds an error and continues deleting the launcher directory and, when requested, the data/token tree (`Uninstaller.cs:142-168,194-200`), leaving the live process holding port 7900 with even fewer ways to stop it. The branch therefore still reproduces the mission's machine-bricking path.

2. **[P0] `tools/cc-director-setup-engine/LauncherStopper.cs:69-89` — the supposedly scoped stop can shut down a launcher from a developer checkout.** The token-gated POST is sent to whoever owns port 7900 before any process is listed or path-scoped. A launcher run from a repository uses the same per-user `LauncherAuth.TokenFile`, so if it owns 7900 and the installed token exists, it accepts `/shutdown` and exits; the later path filter is never reached because lines 78-82 return as soon as the port becomes free. `LauncherStopperTests.Stop_NeverTouchesALauncherOutsideTheInstallDirectory` does not catch this because it creates no token, so its `RequestQuit` delegate is never called (`LauncherStopperTests.cs:110-130`). The fallback filter is also only a raw case-insensitive `StartsWith`; a process under a sibling such as `<LauncherDir>-dev/.../cc-launcher` is treated as installed and killed.

3. **[P1] `tools/cc-director-setup-engine/LauncherMacInstaller.cs:118-146` — a missing launchd PID silently restores the same-version false certification that phase 1.2 was meant to remove.** `TryGetLaunchdPid` is called once, immediately after bootstrap/kickstart, and returns 0 without even adding a diagnostic step when `id`/`launchctl print` fails or the newly submitted job has not acquired a PID yet (`LauncherMacInstaller.cs:212-223`). PID 0 makes `LauncherHealthProbe.PidMatches` accept any responder (`LauncherHealthProbe.cs:68-80`). Concrete path: a same-version unmanaged orphan owns 7900; launchd's new job is still waiting or exits on the single-instance mutex; `launchctl print` has no PID; the orphan's matching-version health response certifies immediately; the existing plist check passes; install reports success for a process launchd does not own. The direct-start production route is gone, which is clean, and `ParseLaunchdPid` parses the shown `pid = N` format correctly; the unsafe zero fallback is the remaining defect.

4. **[P1] `tools/cc-director-setup-engine/LauncherStopper.cs:63-82` — stopping one port owner is incorrectly treated as stopping all installed launchers.** If 7900 is initially free, the method never enumerates processes. If the HTTP quit frees 7900, it also returns before enumeration. Thus an installed launcher that is still starting, failed to bind, runs with another `--port`, or is a second session/process survives while its binary directory is deleted. With two launchers, quitting the one that owns 7900 is enough to report success even though the second installed `cc-launcher` remains. This violates the mission's explicit “no `cc-launcher` process remains” result, and the first test deliberately pins the faulty no-enumeration behavior (`LauncherStopperTests.cs:35-52`).

5. **[P1] `tools/cc-director-setup-engine/LauncherStopper.cs:91-112,130-138` and `tools/cc-director-setup-engine/Uninstaller.cs:142-165` — the result can be false after a successful stop or true before the port is stably free, and `Apply` never gates deletion on it.** If `/shutdown` returns false but the process exits concurrently, an empty process list causes an immediate false result at lines 91-96 without rechecking the port. In the other direction, `WaitForPortFree` accepts the first free sample. Killing a launchd-owned process is an unsuccessful exit, so launchd may restart it after that sample; `Uninstaller` unregisters launchd only afterward and never rechecks the port. `LauncherLaunchdAutostart.Unregister` also ignores a nonzero `launchctl bootout` result and deletes the plist anyway (`LauncherLaunchdAutostart.cs:154-165`), allowing the uninstall report to remain successful while the restarted process binds 7900. The quit-before-wipe call order is present in source, but a failed stop does not prevent the subsequent binary deletion or data wipe, so the ordering does not guarantee the safety the comments claim.

6. **[P1] `src/CcDirector.Launcher/LauncherCore.cs:149-165` — normal, correctly registered launchers are reported as autostart failures.** Both `LauncherAutostart.EnsureRegistered` and `LauncherLaunchdAutostart.EnsureRegistered` document and implement `false` as “already correct” (`LauncherAutostart.cs:25-51`, `LauncherLaunchdAutostart.cs:79-99`). `RegisterAutostartSafe` instead maps `false` to an error. On every ordinary Windows login after the first, the unchanged Run value yields `autostartFailure="the autostart Run key was not written"`. On macOS this is even more deterministic: the installer registers the plist before launchd starts the launcher, so the launcher's self-check sees an already-correct loaded agent and reports failure on the first run. The new tests only prove that the property exists and that `--no-autostart` clears it; they never exercise either real idempotent-success return (`LauncherAutostartVisibilityTests.cs:24-61`).

7. **[P1] `src/CcDirector.Launcher/Program.cs:125-143` and `src/CcDirector.Launcher/LauncherHost.cs:135-169` — the static autostart state can be published before registration and can produce internally inconsistent/stale responses.** Tray mode registers before starting the host, but headless mode starts Kestrel first and registers afterward. During that interval `/healthz` says `autostartOk=true` because the static property is still null. Each endpoint then reads the mutable property twice, so a concurrent write can produce `{ autostartOk: true, autostartFailure: "..." }` in one response. The flyout toggle's enable/failure paths never update `AutostartFailure` at all (`LauncherTrayController.cs:315-342`), so the API can continue reporting a startup-era failure after a successful user repair, or healthy after a later toggle failure.

8. **[P1] `src/CcDirector.Launcher/Program.cs:54-61,99-117` and `src/CcDirector.Launcher/LauncherTrayController.cs:246-263,362-369` — the tray SIGTERM path can deadlock shutdown.** The handler cancels the OS's default SIGTERM and posts `lifetime.Shutdown()` to the UI thread. `ShutdownRequested` synchronously calls `LauncherTrayController.Dispose`, which blocks the UI thread on `_core.StopAsync().GetAwaiter().GetResult()`. `LauncherCore.StopAsync` is asynchronous and can need UI-context continuations, so a SIGTERM on a running tray instance can wedge precisely where the new handler is supposed to make it manageable. A concurrent REST/tray quit is also racy because `_stopped` is a plain check-then-set bool (`LauncherCore.cs:85-89`); two callers can both enter teardown and dispose/null the same clients. During the startup window, merely having an `ApplicationLifetime` causes the signal to be canceled and posted even if the dispatcher is not yet pumping, so the fallback `Environment.Exit` is not guaranteed either.
